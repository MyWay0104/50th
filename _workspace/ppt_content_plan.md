## 2. 전체 이야기와 우선순위

강의의 중심 메시지는 **LLM에게 맡길 일과 데이터·코드·사람이 책임질 일을 구분하며 작은 업무 도구를 만든다**이다.

오전에는 모델을 직접 호출해 출력의 특성을 관찰한다. 답변에 필요한 외부 근거를 연결하고, 정확한 조회·계산을 위한 Tool을 붙인 뒤 화면에서 사용해 본다. 오후에는 같은 프로그램을 Claude Code로 읽고 개선한다. 이어서 작업 경험과 자료를 근거 있는 지식으로 정리하고, 각자 선택한 업무에 적용한다.

| 구분 | 포함할 내용 | 분량 결정 이유 |
| --- | --- | --- |
| 본문 필수 | 토큰·Attention의 직관, 학습/추론, 모델·서버·API·SDK, temperature | 첫 호출에서 무엇을 바꾸는지 이해하기 위함 |
| 본문 필수 | RAG, 본문·출처 확인, Tool 실행 순서, SQL 조회·조건 검증, Agent 정의 | 오전 실습 각 단계가 필요한 이유를 설명 |
| 본문 필수 | 작은 구조 설계, 좋은 요청, 탐색·계획·구현·검증, 기본 기술 역할 | 오전 결과물을 오후 작업 대상으로 연결 |
| 본문 필수 | CLAUDE.md·작업 기록, Raw/개인 의견/Wiki, Skill 하나, 다른 입력으로 검증 | 수업 이후에도 반복할 수 있는 작업 방법 |
| 짧게 언급 | MCP·Subagent·Hook의 역할, 비용·응답 시간, 운영 권한 | 선택 기준만 제공하고 상세 설정을 줄임 |
| 부록 | Transformer 수식, 프레임워크 상세 비교, MCP 서버 구축, 다중 Agent 운영 | 현재 40분 단위 실습에 필수적인 선행 지식이 아님 |

아키텍처 회고는 오전 앱을 만든 후인 4차수에 배치했다. 강사의 실패 경험이 실제로 방금 본 구조와 연결되도록 하기 위해서다. Dokmo는 사용성 검증 사례로, Part Finder는 후보·조건 검증 사례로, Obsidian은 출처와 개인 판단을 구분하는 사례로 각각 사용한다.

## 3. 운영 전제와 지연 시 조정

오전 120분에 모든 기능을 빈 파일부터 작성하는 목표는 잡지 않는다. 사전에 제공한 코드에서 핵심 옵션·함수·연결 부분을 수정하는 방식이다. 이론에서 본 요소의 코드 위치를 찾고, 실행 결과를 확인하는 데 시간을 사용한다.

| 상황 | 유지할 핵심 | 줄이거나 바꿀 부분 |
| --- | --- | --- |
| 첫 API 접속 지연 | 요청·응답·temperature 비교 | 사전 저장 출력으로 비교. 계정·네트워크 해결로 전체 수업을 멈추지 않음 |
| 기사 접근 실패 | 본문·출처·검색 근거 확인 | 교육용으로 준비한 저장 본문 사용 |
| SQL 연결 지연 | 스키마·도구 호출·결과 검증 | 동일 구조의 교육용 DB 또는 준비된 도구 결과 사용 |
