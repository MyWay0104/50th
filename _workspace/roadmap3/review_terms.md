## 3. ROADMAP3 9절 ⑦⑧⑪에 대한 답

### ⑦ "쥐여 주기" · "손으로 돌려 본 반복"

**(가) "직접 반복문으로 돌려 본 호출"은 반만 맞다. 그대로 쓰면 안 된다.**

- 틀린 점 ①: **"호출"은 루프가 아니다.** Agent 루프의 가장 작은 모양은 한 번의 호출이 아니라 **요청 → 실행 → 결과 전달의 되풀이**다. S16의 카드 ②③④가 이미 그 되풀이를 가르쳤다.
- 틀린 점 ②: 어순. "직접 반복문으로"는 부사구로 읽혀 *누가* 직접 한 것인지 흐려진다. R2-14가 살리려던 사실은 "그 반복문이 실습 코드에 적혀 있었고 수강생이 그것을 돌렸다"이다.
- **권장 표현: `반복문으로 직접 돌린 도구 호출 반복`** — T03 화면·노트, N03, LAB04b 노트에서 같은 글자로 쓴다. 좁은 칸에서는 **`실습 04b의 도구 호출 반복`**으로 줄인다.
- 그리고 **N03에서는 이 표현을 정의로 쓰지 말 것**(H3). 정의는 "모델이 결과를 보고 다음 도구 호출을 정하는 반복"이고, "실습 04b의 그 반복"은 정의가 아니라 **되짚기**다. 정의와 되짚기를 한 문장에 겹쳐 놓으면 "Agent 루프 = 반복문"이라는 오개념이 남는다.

**(나) "쥐여 주기"는 함께 정리해야 한다.**

`bind_tools`가 하는 일은 **도구의 이름·설명(docstring)·입력 형식을 모델 호출에 함께 실어 보내는 것**이다(4일 교안 p47–51 `@tool`·p132–136 `bind_tools`). "쥐여 준다"는 손 비유이자 "모델이 도구를 갖고 있게 된다"는 오해를 준다.

- **권장: `도구 연결` / `도구 연결(bind_tools)`.** 코드 주석·카드에서는 `연결`, 문장에서는 `연결합니다`.
- **`등록`은 권하지 않는다** — 어딘가에 등록해 두면 그다음부터 자동으로 쓰인다는 오해를 준다(실제로는 매 호출마다 도구 정의를 같이 보낸다).
- 바꿀 자리는 4곳뿐이고 **글자는 6자 줄어든다**(M13).

### ⑧ `데이터 조회용 액세스 토큰` / `데이터 조회용 토큰` 병행

**권하지 않는다. 덱 전체를 `데이터 조회용 토큰` 한 이름으로 통일할 것을 권한다.**

1. **병행이 실제로 지켜지지 않았다.** "정의 자리 E01만 긴 이름"이라는 규칙인데 LAB06 칩(P3)과 A05 노트(P4)가 긴 이름을 썼다(M2·M3). 규칙이 네 묶음 중 두 묶음에서 깨졌다는 것은 규칙 자체가 지키기 어렵다는 뜻이다.
2. **"액세스 토큰"은 확인되지 않은 규정이다.** 확정 사실은 "다른 플랫폼에서 발급하는 JWT 토큰이고 만료된다"까지다. 액세스 토큰이라고 이름 붙이면 갱신 토큰과의 짝 개념까지 끌고 들어오는데 확인된 바 없다. R2-21의 "확인 전 단정 금지" 정신에 맞지 않는다.
3. **401 진단이 흐려진다.** 오늘 수강생이 구분해야 할 것은 딱 두 가지다 — *API 키(채팅용·임베딩용)* vs *데이터 조회용 토큰*. 이름이 하나 더 늘면 401 안내에서 "어느 키인지"를 고르는 시간이 늘어난다.
4. 통일하면 화면 글자도 **약 12자 줄어든다**(3곳 × 4자).

**대신 E01 정의 자리에서 성질을 문장으로 설명한다**(이미 그런 문장이 있다): `사내 LLM 게이트웨이 밖, 다른 플랫폼에서 발급합니다 · Tool 실습에서 받습니다 · 만료됩니다`. 이 한 줄이 "액세스 토큰"이라는 이름보다 실습에서 쓸모가 크다.

### ⑪ `채팅용 키` → `채팅용 API 키` 통일

**맞다. 통일이 옳고, 실습자료의 실제 개념과도 어긋나지 않는다.**

- 근거: 요약본 실습 01 STEP 2는 사내 LLM Ops에서 **Chat용 팀 키**와 **Embedding용 팀 키** 2종을 별도 발급한다고 적었고, 실습 06 STEP 2는 **"실습 01에서 발급한 그 키를 그대로 사용"**한다고 적었다. 팀 단위로 발급되든 개인 단위로 발급되든 **모델 호출용 API 키**라는 성질은 같으므로 `채팅용 API 키`가 정확하다. R2-5("오전과 오후가 같은 계열 키")와도 맞는다.
- 통일해야 하는 더 큰 이유: `채팅용 키`와 `데이터 조회용 토큰`이 나란히 놓이면 **"키"와 "토큰"이 서로 다른 종류처럼** 보인다. 세 가지를 묶는 상위 이름은 `인증 키 3종`이고, 그 아래 둘은 API 키, 하나는 토큰이라는 구조가 화면에서 한눈에 보여야 401 안내가 작동한다.
- **단, 대명사적 축약은 허용한다.** 바로 앞 문장이 어떤 키인지 이미 특정한 경우의 `같은 키` · `키 칸` · `키 값`은 그대로 둔다(S23 강조 칩 `같은 게이트웨이 · 같은 키`, E01 `오후에도 같은 키를 씁니다`, LAB01 `키 칸`). 좁은 칸이라 짧게 쓰는 것이 아니라, **지시 대상이 이미 정해졌기 때문에** 짧게 쓰는 것이다.
- **통일 대상은 표 밖에도 있다.** `채팅용 키`는 덱에 20곳 있고, 그중 **G03(점심 안내 화면·노트 3곳)과 S29(웹앱 세 층 노트 1곳)는 어느 묶음 표에도 들어 있지 않다.** 이 두 장면은 비유가 없어 담당이 배정되지 않았다. T4 일괄 치환에 반드시 포함할 것.
  - S29 노트의 `모델에는 채팅용 키로, 사내 데이터에는 데이터 조회용 토큰으로 각각 요청합니다.`는 두 인증 수단을 대비시키는 유일한 문장이므로 → `모델에는 채팅용 API 키로, 사내 데이터에는 데이터 조회용 토큰으로 각각 요청합니다.`
- 함께 처리: M14(설정 파일의 인증 토큰 칸 = 채팅용 API 키라는 한 문장)를 LAB06 노트에 넣으면 이 통일이 완성된다.

4. 묶음 간 불일치는 **네 묶음이 각자 좋은 판단을 했기 때문에** 생겼다(401 구절·조회용 토큰 이름·여섯 단계·띠 부제). 모두 글자 맞추기로 끝나고, 내용 판단이 필요한 것은 없다.
5. ⑦⑧⑪ 세 질문의 답은 각각 **"고쳐서 쓰되 표현을 바꾼다 / 병행하지 말고 짧은 이름으로 통일한다 / 통일이 맞고 표 밖 2장면을 놓치지 말 것"**이다. 세 가지 모두 글자가 늘지 않고 줄어든다.
