첫 번째 방향은 코드를 짜 달라고 하지 않고 "이 파일에서 장비별 건수를 세 주세요"처럼 결과를 요청하는 방식입니다. 왼쪽 그림처럼 Claude Code는 그 요청을 받아 스스로 Python 스크립트를 쓰고 실행해서 표나 그래프를 만들고, 마지막에 모델이 그 결과를 설명합니다. 여기서 숫자를 세는 것은 코드이고 모델은 요청을 이해하고 결과를 풀이하는 역할만 맡는데, 오전 계산 도구에서 계산은 코드가 했던 것과 같은 원칙입니다. 시연을 보기 전에 하나만 예측해 보세요. 결과 표의 숫자가 맞는지 우리는 무엇으로 확인할 수 있을까요? 오른쪽 시연 화면, 또는 제 화면으로 가상 CSV 집계의 같은 흐름을 보여 드리겠습니다. 결과 표가 나오면 그대로 믿지 말고 원본 파일에서 한두 값을 골라 한 번 대조하는데, 이것이 이 방향의 검증 습관입니다. 시연을 보면서 어느 대목이 코드가 한 일이고 어느 대목이 모델이 한 일인지 나눠 보고, 시연이 끝나면 코드가 한 일 하나와 모델이 한 일 하나를 옆 사람에게 한 줄로 말해 주세요.

출처: Claude Code 공식 문서 Best practices

"앱 개선해 주세요"라고만 하면 Claude Code는 무엇을 어디까지 바꿀지 스스로 추측해야 하고, 우리도 결과를 받았을 때 끝난 것인지 판단할 기준이 없습니다. 아래 여섯 칸처럼 목표, 입력과 출력, 바꿀 범위, 지켜야 할 제약에 더해 어떤 입력에서 어떤 결과가 나오면 끝인지를 적으면 작업 방향과 확인 방법이 함께 정해지고, 공식 모범사례도 확인할 수 있는 기준을 요청에 함께 주라고 권합니다. 예시는 오전에 만든 장비 조회 Agent에 없는 장비 ID 안내를 붙이는 요청문입니다. 특히 주황 칸의 완료 조건처럼 기존 질문의 결과가 그대로여야 한다는 조건을 넣어 두면, 새 기능을 붙이다 원래 기능을 망가뜨렸는지 확인할 수 있습니다. 오류 없이 실행되는 것, 결과가 정확한 것, 사용자의 목적에 맞는 것은 각각 따로 확인할 대상입니다. 이제 오전에 만든 장비 조회 Agent에 붙이고 싶은 기능 하나의 완료 조건을 "어떤 입력에서 무엇이 나오면 끝"이라는 한 문장으로 적어 보세요. 이 문장이 자유 실습이나 선택 과제의 입력이 되니, 두 분 정도 읽어 보겠습니다.

출처: Claude Code 공식 문서 Best practices

방향 ②의 시연 대상은 앞 장 요청문 그대로, 오전에 만든 장비 조회 Agent에 결과 없음 안내를 붙이는 것입니다. 이 시연을 네 단계로 끊어서 보여 드리겠습니다. 네 카드 순서대로, 먼저 Claude Code에게 현재 구조와 지금의 정상 동작을 설명하게 하고, 바꿀 곳과 완료 조건을 계획으로 받아 우리가 읽어 본 뒤, 계획한 범위만 수정하게 하고, 새 기능과 기존 기능을 둘 다 실행해 확인합니다. 각 카드의 산출물 줄은 그 단계가 끝났을 때 손에 남는 것, 곧 구조 설명·계획 문서·바뀐 줄·실행 결과이고, 검증에서 문제가 보이면 탐색으로 되돌아갑니다. 공식 모범사례도 여러 파일을 바꾸거나 방법이 불확실할 때 계획을 먼저 세우라고 권하며, 한두 줄짜리 작은 수정까지 긴 계획을 세울 필요는 없습니다. "마지막 정상 지점과 첫 실패 지점을 증거로 말하기"도 같은 습관이어서, 단계마다 산출물이 남아 있어야 어디까지 정상이었는지 말할 수 있습니다. 시연 중간에 화면을 멈추고 "지금 어느 단계였나요?"라고 물을 테니 네 카드 중 하나를 손가락으로 가리켜 주세요. 계획이 나왔을 때도 한 번 멈출 테니, 그 계획에서 범위 밖인 줄이 있는지 찾아 옆 사람에게 말해 주세요. 고치기 전에 정상 동작을 먼저 확인해 두어야 하는 이유는 무엇일지 한 분만 짧게 답해 주세요.

방향 ② · 스크립트와 작은 앱 만들기

완료 조건에 '없으면 없다고 답한다'를 넣어야 쓸 수 있는 도구가 됩니다.

출처: Claude Code 공식 문서 Best practices

방금 시연한 것이 두 번째 방향, 원래 목적인 coding agent이고, 왼쪽처럼 엑셀 두 파일을 비교해 다른 행을 뽑는 스크립트 같은 작은 프로그램을 만드는 것입니다. 여기서 핵심은 코드를 잘 짜 달라는 말이 아니라 완료 조건이어서, 같은 파일이면 '차이 없음'이라고 답해야 한다는 조건이 없으면 스크립트가 빈 화면을 내놓아도 그것이 끝난 것인지 알 수 없습니다. 오른쪽은 제가 만든 부품 번호 검색 도구의 공개 Beta 설계를 단순화한 가상 표인데, 자랑이 아니라 완료 조건의 예로 보시면 됩니다. 요청문에 검색 후보에 있는 Part Number만 쓰고, 종류와 제조사 조건이 다 맞을 때만 답하며, 맞는 후보가 없으면 '없음'이라고 답하라는 조건을 넣었고, 그 검증은 모델이 아니라 코드가 맡습니다. 제조사 A의 로봇 블레이드를 찾는데 같은 제조사의 O-ring만 있다면 그럴듯한 답 대신 "조건에 맞는 후보 없음"이 업무에 쓸 수 있는 답입니다. 개인 기록으로 한 가지 덧붙이면, 개발 후반에 작은 수정 하나가 여러 곳에 번져 고치기 어려웠던 경험이 있어서 지금은 바꿀 범위를 먼저 정하고 요청합니다. 이 표는 공개 설계를 단순화한 것이고, 현재 사내 운영 버전과 같다는 뜻은 아닙니다. 여러분이라면 엑셀 비교 스크립트의 완료 조건에 '차이 없음' 말고 무엇을 하나 더 넣겠습니까? 한 분만 답해 주세요.
