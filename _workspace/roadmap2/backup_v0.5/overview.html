실습 환경의 세 층

코드는 내 PC에서 돌고, 계산은 사내 추론 서버에서 하며, 환경변수가 둘을 잇습니다.

설치는 사전 과제로 마쳤으니 오늘은 세 층이 이어지는지만 확인합니다. 코드에 OpenAI라는 이름이 있어도 요청은 환경변수에 적은 서버로 갑니다.

출처: vLLM Online Serving 문서 · LangChain Models 문서

실습 환경은 세 층으로만 기억하시면 됩니다. 코드는 내 PC의 VS Code와 Python에서 돌고, 실제 계산은 사내 추론 서버에서 vLLM이 모델을 실행해 처리하며, 그 둘을 잇는 것이 서버 주소, 모델 이름, 키 세 개의 환경변수입니다. 환경변수 값은 사내 모델 운영 페이지에서 받아 코드 밖에 두고, 오른쪽 코드의 model과 base_url 두 줄이 그 값을 읽어 요청의 목적지를 정합니다. 그래서 코드에 OpenAI라는 이름이 있어도 요청이 OpenAI로 가는 것은 아니고, API는 요청과 응답 형식의 약속, SDK나 LangChain은 그 호출을 돕는 Python 도구라는 정도만 알아 두시면 됩니다. VS Code, Python, Claude Code 설치는 사전 과제로 마치셨으니 오늘은 첫 호출이 되는지만 확인하고, 첫 응답이 오면 content와 함께 토큰 사용량도 같이 보겠습니다. 이 토큰이 오늘 내내 길이와 비용을 재는 단위입니다. 질문 하나 드리겠습니다. 환경변수 한 줄이 틀리면 세 층 중 어디에서 막힐까요? 주소가 틀리면 서버에 닿지 못하고, 모델 이름이 틀리면 서버가 거절하고, 키가 틀리면 인증에서 막힙니다.

LLM의 응답 생성

LLM은 사실을 조회하지 않고 다음 토큰의 확률 분포를 계산합니다.

보통의 호출은 학습된 모델로 계산만 하므로, 질문을 더 보낸다고 모델이 재학습되지 않습니다. 한 번에 넣을 수 있는 입력·출력 길이의 한도를 컨텍스트 윈도우라고 합니다. 다음 실습에서 바꿀 temperature 값은 3단계의 선택에 영향을 줍니다.

  1. 1
    토큰으로 나누기회의 | 내용을 | 세 | 줄로
  2. 2
    다음 토큰 분포 계산후보: 요약 · 정리 · …
  3. 3
    선택하고 반복'요약'을 골라 뒤에 붙임
고른 토큰을 입력 끝에 붙여 2단계로 돌아가기 — 답이 끝나거나 길이 한도에 닿을 때까지 반복

개념 예시 · 실제 토큰 분할은 모델마다 다름 · 확률 수치 없음 · 길이 한도 = 컨텍스트 윈도우

출처: Vaswani et al. 2017 · Ouyang et al. 2022 (지시 수행 학습)

용어를 먼저 정리하면, AI 안에 데이터로 패턴을 학습하는 머신러닝이 있고 그 안에 신경망을 쓰는 딥러닝이 있으며, 오늘 다루는 LLM은 딥러닝 기반의 언어 모델입니다. 대체 관계가 아니라 포함 관계이고, 오늘은 그중 LLM이 답을 만드는 방식만 가져갑니다. LLM은 입력을 토큰이라는 단위로 나누고, 지금까지의 문맥으로 다음 토큰 후보들의 가능성을 계산해 하나를 고르는 과정을 반복합니다. 화면의 세 카드 아래 줄처럼, 고른 토큰을 입력 끝에 붙여 다시 2단계로 돌아가는 방식을 자기회귀 생성이라고 합니다. 토큰은 단어 하나와 항상 같지 않고, 나누는 방식은 모델마다 다릅니다. 학습 단계에서는 모델 매개변수를 바꾸지만, 오늘 우리가 하는 호출은 이미 학습된 모델로 결과를 계산할 뿐입니다. 토큰 수는 비용과 속도를 재는 단위이면서, 한 번에 넣을 수 있는 입력과 출력 길이의 한도인 컨텍스트 윈도우를 재는 단위이기도 합니다. 이 한도는 다음 RAG 구간에서 자료를 나누는 첫 이유로 다시 나옵니다. 그러면 재학습이 아닌데도 같은 질문의 답이 달라진다면, 세 단계 중 어디에서 갈리는지 한 분만 답해 주세요.

temperature는 다음 토큰을 고를 때 선택의 다양성에 영향을 주는 값입니다. 화면의 막대처럼 같은 후보라도 값을 낮추면 확률이 높은 후보 쪽으로 몰리고, 높이면 여러 후보로 퍼져서 표현이 호출마다 달라지기 쉽습니다. 하지만 어느 쪽이든 모델이 모르는 정보를 더하거나 사실을 검증해 주지는 않습니다. 낮은 값에서도 틀릴 수 있고, 서버 환경에 따라 모든 실행이 완전히 같다는 보장도 없습니다. 같은 선택 단계에서 후보 범위를 좁히는 Top-K·Top-P 같은 값도 있지만, 오늘 실습에서는 temperature 하나만 바꿔 봅니다. 같은 질문을 여러 번 보내면 어떤 차이가 날지 먼저 예측해 보세요.

메시지 역할과 프롬프트

system이 규칙을 정하고, user가 묻고, assistant가 답합니다.

모델에 보내는 것은 문장 하나가 아니라 역할이 붙은 메시지 목록입니다. 모델은 목록에 있는 것만 보므로, 앞의 답을 다시 넣지 않으면 이전 대화를 모릅니다.

system규칙·말투·역할한 줄이 답 전체를 바꿈
user이번 질문매번 새로 보냄
assistant모델의 답다음 요청에 다시 넣어야 기억
예시 몇 개를 함께 넣으면 답의 모양이 예시를 따릅니다
역할이 붙은 메시지 목록 · 개념 예시
messages = [
  ("system", "정중하게 답합니다"),   # 규칙
  ("user", "첫 질문"),
  ("assistant", "첫 답"),  # 앞 답을 다시 넣음
  ("user", "두 번째 질문"),
]

코드 위치: 프롬프트 구성부 · 긍정봇 — 실습 가이드 해당 장

출처: LangChain Messages 문서 · OpenAI Chat Completions 가이드

모델에 보내는 것은 문장 하나가 아니라 역할이 붙은 메시지 목록이고, 역할은 세 가지만 기억하시면 됩니다. system은 규칙과 말투와 역할을 정하는 자리라 한 줄만 바꿔도 답 전체의 성격이 바뀌고, user는 이번 질문이며, assistant는 모델이 낸 답입니다. 오른쪽 코드처럼 앞의 답을 assistant 메시지로 다시 넣어야 모델이 이전 대화를 참고할 수 있고, 넣지 않으면 매번 처음 만난 것처럼 답합니다. 이 성질은 이어지는 실습의 긍정봇에서 직접 확인합니다. 아래 상자의 한 줄처럼 원하는 답의 예시를 몇 개 같이 넣으면 답의 형식과 말투가 그 예시를 따라오는데, 이 방식을 few-shot 프롬프팅이라고 부릅니다. 예측 질문 하나 드리겠습니다. system 한 줄을 바꾸면 답의 무엇이 달라질까요? 내용이 달라질지, 말투와 형식이 달라질지 예측해 두시고 실습에서 확인해 보세요.

나누고, 숫자로 바꾸고, 가까운 것 찾기

긴 자료는 조각으로 나누고, 조각을 뜻이 담긴 숫자로 바꿔 두면 가까운 조각을 찾을 수 있습니다.

한 번에 넣을 수 있는 길이에 한도가 있고, 자료가 크면 질문과 관계없는 부분까지 섞이므로 나눕니다. 나눈 조각을 숫자 묶음으로 바꿔 두면, 질문과 뜻이 가까운 조각만 골라 모델에 넘길 수 있습니다.

  1. ① 나누기 · 청킹
    긴 자료를 조각으로조각 크기 · 겹침

    가까운 뜻은 가까운 숫자로조각마다 숫자 묶음
  3. ③ 가까운 것 찾기 · 벡터 검색

RAG 기본 구조 장면에서 기사가 100편이면 다 못 넣는다고 했는데, 그러면 무엇을 해야 할까요? 첫째, 긴 자료를 조각으로 나눕니다. 컨텍스트 윈도우 한도 때문이기도 하고, 조각이 작아야 질문과 관계있는 부분만 정확히 찾을 수 있기 때문이며, 실습 코드의 chunk_size가 조각 크기이고 조각끼리 조금 겹치게 하는 값이 overlap입니다. 둘째는 벡터 저장소 장면에서 본 '뜻을 숫자로 바꾸기', 곧 임베딩입니다. 아래 예시처럼 반도체 공정과 웨이퍼 제조는 숫자가 가깝고 맛있는 김치는 멀리 있는데, 가깝다는 것은 두 숫자 묶음 사이 거리나 코사인 값으로 계산합니다. 셋째, 질문도 같은 방식으로 숫자로 바꿔 저장소에서 가까운 조각 몇 개만 꺼내는 것이 벡터 검색이고, 실습에서 쓰는 저장소는 앞 장에서 본 FAISS입니다. 오늘 실습은 ②까지, 곧 나누고 임베딩해 저장하는 데까지 손으로 하고, ③은 저장해 둔 조각을 나중에 어떻게 쓰는지로만 봅니다. 먼저 기사 페이지에서 본문을 가져와 제목과 본문 길이, 대표 문단이 실제로 들어왔는지 눈으로 확인합니다. 여기까지는 AI 없이 찾아서 읽기만 한 것입니다. 이어서 본문을 나누고 저장소에 넣은 뒤 조각이 몇 개 나왔는지 세고, chunk_size를 바꿔 다시 세어 봅니다. 조각이 두 개면 통째로 넣어도 되는데 왜 나누냐고 물으실 텐데, 기사가 많아지면 컨텍스트 윈도우에 다 못 넣기 때문이고, 오늘은 그 방법을 작은 크기로 미리 손에 익히는 것입니다. 다음으로 본문을 질문에 붙여 요약하게 하는데, 이것은 외부 문서 기반 요약이고 질문에 맞는 조각을 골라 넘길 때 비로소 RAG라 부릅니다. 요약의 한 문장을 고르고 그 문장이 본문 어디에 있는지 찾아 대조하고, 마지막으로 기사에 없는 것을 물어 없다고 답하는지 확인합니다. 없다고 답하지 않고 아는 척 답하면, 프롬프트에 '본문에 없으면 없다고 답한다'는 제약이 있는지 먼저 봅니다. 다음 장의 답변 쪽 점검이 바로 이것입니다. 기사 접속이 안 되는 분은 준비된 저장 본문으로 같은 단계를 진행합니다.

답변과 검색 근거 확인

틀렸다면 검색이 틀렸는지, 근거를 잘못 설명했는지부터 나눕니다.

RAG 품질은 검색(관련 조각을 가져왔나)과 답변(근거에 충실했나)으로 나눠 봅니다. 검색 문제면 분할·검색 방식을, 답변 문제면 프롬프트 제약을 고칩니다. 정확한 집계 질문은 다음 구간의 도구(Tool)로 넘깁니다.

근거 있는 답은 되지만 정확한 숫자와 지금 상태는 못 내므로, 다음은 코드가 실행하는 도구입니다.

도구(Tool) 호출 순서

모델은 도구 호출을 요청하고, 실행은 프로그램이 합니다.

프로그램이 도구의 이름·설명·입력 형식을 알려 주면 모델은 부를 도구 이름을 담은 호출 요청을 돌려줍니다. @tool은 docstring이 곧 도구 설명이라 모호하면 잘못 고릅니다. 이 도구는 인자가 없어 모델은 '부를지 말지'만 정합니다.

  1. ① 프로그램
    도구 알려주기이름·설명·형식
  2. ② 모델
    호출 요청tool_calls
  3. ③ 프로그램
    실행과 반환조회 결과
  4. ④ 모델
    결과로 응답답변 또는 다시 ②로

④에서 도구 호출이 더 없으면 답하고 끝냅니다 · 더 있으면 ②로 돌아가 반복합니다

@tool  # 교육용 가상 함수 · 인자 없음
def equipment_status() -> list:
    """장비별 현재 위치와 진행 공정"""

"모델이 도구를 쓴다"는 말은 모델이 Python 함수를 자기 안에서 실행한다는 뜻이 아닙니다. 화면 네 카드의 위쪽 라벨은 그 단계를 누가 하는지, 카드 아래 작은 줄은 각 단계에서 오가는 내용입니다. LangChain 코드에서는 각 단계를 도구 스키마, tool_calls, ToolMessage, AIMessage라는 이름으로 부릅니다. 프로그램이 도구 스키마를 알려 주면 모델은 tool_calls에 도구 이름을 담아 요청만 하고, 실제 함수나 SQL은 프로그램이 실행해 결과를 ToolMessage로 돌려주며, 모델은 그 결과를 보고 답하거나 도구가 더 필요하면 다시 ②로 돌아가 요청합니다. 도구 호출이 더 없을 때 답하고 끝나는 것이 이 반복의 종료 조건이고, 오후에 볼 Claude Code도 같은 반복 구조입니다. 아래 코드처럼 @tool은 함수 이름, docstring, 타입 힌트로 도구 설명을 만들기 때문에 docstring은 동료에게 설명하듯 써야 하고, 이번 실습의 도구는 인자가 없어 모델이 정하는 것은 이 도구를 부를지 말지뿐입니다. 도구 호출은 모델의 '행동'이고, 그 권한과 부작용은 실행하는 프로그램 쪽에서 책임집니다.

부록 · Transformer와 Q·K·V

Attention은 Q·K 비교로 정한 비율대로 V를 모읍니다.

비율은 입력마다 새로 계산되는 값이며 학습된 매개변수와 다릅니다. 원 논문은 encoder–decoder 구조이고, 많은 생성 모델은 decoder 중심입니다.

  • Q·K·V 찾는 기준·이름표·내용비유 · 한 토큰 표현에서 나온 세 벡터
  • 그림 왼쪽: 헤드 하나의 계산softmax(QKT / √d) · V
  • 그림 오른쪽: 여러 헤드를 나란히헤드 = Q·K·V 계산 한 벌 · 헤드마다 다른 변환

Vaswani et al. (2017), Figure 2 · arXiv:1706.03762

출처: Vaswani et al., Attention Is All You Need (2017) · arXiv:1706.03762

오전 응답 생성 장면에서 모델이 문맥을 보고 다음 토큰을 고른다고 했는데, 그 문맥을 반영하는 계산이 Attention이고 그 재료가 Q·K·V이며, 비유하면 Q는 찾는 기준, K는 비교될 이름표, V는 실제로 전달할 내용입니다. 화면 오른쪽 원 논문 그림 중 왼쪽이 헤드 하나의 계산으로, 아래에서부터 Q와 K를 곱해 비교하고 크기를 조정한 뒤 softmax로 반영 비율을 만들어 그 비율대로 V를 모읍니다. 중간의 Mask는 선택 단계인데, 생성 모델은 이것으로 아직 나오지 않은 뒤쪽 토큰을 가립니다. 오른쪽 그림은 서로 다른 변환을 가진 여러 헤드가 이 계산을 나란히 한 뒤 이어 붙이는 구조이고, 실제 모델은 이것을 여러 층에서 반복합니다. 이 비율은 입력마다 새로 계산되는 값이라 학습된 매개변수와 다르며, 그림은 구조도이지 가중치를 측정한 결과가 아닙니다. 원 논문은 번역을 위해 encoder와 decoder를 함께 썼고, 오늘날 많은 생성 모델은 앞쪽 토큰만 참고하도록 가린 decoder 중심 구조를 씁니다. 원 논문 이후 여러 공개 모델은 RMSNorm, SwiGLU, RoPE 같은 변형을 쓰지만, Q·K 비교로 비율을 정해 V를 모으는 원리는 같습니다.

MCP 서버가 내놓는 것은 도구, 자료, 프롬프트 세 가지이고, 승인된 문서나 DB를 읽는 식으로 쓰되 기존 파일·명령 도구로 충분하면 추가하지 않아도 됩니다. Subagent는 예외 입력 점검이나 설정 위치 조사처럼 독립적인 하위 작업을 별도 맥락에서 맡기고 결과만 돌려받는 방식인데, 여러 개를 쓰면 비용과 조정 작업도 늘어납니다. Hook은 파일 수정 후 포맷처럼 정해진 시점에 설정된 동작을 실행하며, 명령을 실행하는 유형과 모델 판단을 쓰는 유형이 따로 있습니다. 네 기능은 상하위 단계가 아니라 서로 다른 역할이라 필요하면 함께 조합하고, 실제 설치와 권한 설정은 사내 가이드의 승인된 방법을 따릅니다. CLAUDE.md에 적은 지침은 모델이 읽는 안내일 뿐 권한을 강제하지 않는다는 점도 기억해 두세요.

부록 · Agentic RAG

검색 결과를 평가해 부족하면 질문을 고쳐 다시 찾습니다.

앞의 RAG 구간에서 본 '검색이 틀렸나' 확인을 그래프에 넣은 구조입니다. 모델이 문서마다 관련성을 yes/no로 매기고, 그 결과로 경로가 갈립니다. 판정마다 호출이 늘어 재시도 횟수를 제한합니다.

검색retrieve
→

→yes
답변 생성generate
↓ no
질문 재작성다시 검색으로 · 횟수 제한
개념 예시
관련성 판정 스키마 · 교육용 축약(일부 줄 생략)
class GradeDocuments(BaseModel):
    score: Literal["yes", "no"]
grader = model.with_structured_output(
    GradeDocuments)
grade = grader.invoke(prompt).score

출처: LangGraph Agentic RAG 문서 · Lewis et al. 2020

앞의 RAG 구간에서 답이 틀리면 검색이 틀렸는지, 가져온 자료를 잘못 설명했는지부터 나눠 보자고 했는데, Agentic RAG는 그 판단의 일부를 그래프 안에 넣은 구조입니다. 화면 왼쪽 그림처럼 검색한 뒤 모델이 문서마다 질문과 관련 있는지 yes나 no로 판정하고, 관련 문서가 있으면 답변을 만들고 없으면 질문을 고쳐 다시 검색합니다. 오른쪽 코드는 그 판정을 정해진 형식으로 받도록 yes와 no 두 값만 허용하는 스키마를 모델에 연결하는 부분을 교육용으로 줄인 것입니다. 이 그림에서 모델이 하는 일은 관련성 판정이고, 어느 길로 갈지는 그 결과를 받은 조건부 Edge가 정한다는 점도 봐 두세요. 같은 계열인 Corrective RAG는 근거가 부족하면 웹 검색으로 보완하고, Self-RAG는 답변이 근거에 맞는지까지 평가하며, Adaptive RAG는 질문에 따라 검색을 안 할지, 한 번 할지, 여러 번 할지를 먼저 고르는데, 사내망에서는 웹 검색 자체를 쓸 수 없을 수도 있습니다. 판정 한 번마다 모델 호출이 늘어 시간과 비용이 커지므로 재검색 횟수에 상한을 두고, 상한에 닿으면 억지로 답하지 않고 근거를 찾지 못했다고 알리게 합니다. 평가 단계를 넣었다고 환각이 사라지는 것은 아니니 근거 확인은 계속 필요합니다. 오늘 실습한 기본 RAG로 충분한지부터 확인하세요.

Deep Agents는 LangGraph 위에 작업 계획 목록, 허용된 경로 안의 파일 도구, 긴 출력을 파일로 넘기는 오프로딩, 하위 작업 위임을 미리 묶어 둔 하네스이고, 오른쪽 코드는 그 설정의 인자 이름만 보여 주며 값은 생략했습니다. Claude Code도 하네스라고 했지만 LangGraph나 Deep Agents로 만든 것은 아니고, 모델을 둘러싼 실행 틀이라는 역할이 같다는 뜻입니다. 다음 장에서 볼 사내 배포 패키지 예시도 이런 구성으로 만든 참고 예시입니다. 다만 도구 몇 개를 짧게 호출하는 작업이라면 create_agent로 충분하고, 하네스 기능은 긴 작업, 파일 작업, 사람 승인 같은 요구가 생길 때 고르면 됩니다. 인자 이름은 설치 판본에 따라 달라질 수 있으니 공식 문서에서 확인하세요.

삭제, 셸 실행, 외부 시스템 변경처럼 되돌리기 어려운 행동은 모델이 요청하더라도 사람이 한 번 보고 결정하게 하는 것이 안전합니다. 화면 왼쪽 그림처럼 모델이 도구 호출을 요청하면 interrupt()로 그래프를 멈추고, 사람이 승인하면 도구를 실행하고, 거부하면 그 사유를 모델에게 돌려줍니다. 사람의 결정은 Command(resume)로 전달해 멈춘 곳부터 이어가는데, 멈춘 상태를 저장해 둘 체크포인터가 있어야 하고, 저장된 상태는 나중에 조회해 어느 시점에서 멈췄는지 확인할 수도 있습니다. 앞 장 코드의 interrupt_on처럼 Deep Agents에서는 어떤 도구 앞에서 멈출지 설정으로 선언만 해도 같은 효과를 냅니다. 오른쪽 화면은 사내 배포 패키지 예시로, 셸 명령을 실행하기 전에 도구 이름과 명령을 보여 주고 승인과 거부를 받는 장면입니다. 수강생 실습 화면은 아니고, 승인 카드 부분만 잘라 보여 드립니다. 오후 실습에서 Claude Code가 파일 수정이나 명령 실행 전에 승인을 요청했다면 그것도 같은 발상의 장치이고, CLAUDE.md나 프롬프트에 "하지 마"라고 적는 문장은 이런 멈춤 장치를 대신하지 못합니다.
