## S29 · 웹앱의 입력부터 데이터까지

- data-skill: `split` (`.wide-left` 권장)
- eyebrow: `B5` · `Claude Code로 앱 개선`
- 제목: 웹앱의 입력부터 데이터까지
- 시각 쪽 (코드 카드 `.code-card`, 5줄)
  - 성격 배지: 개념 예시
  - 코드 제목: 한 파일 안의 화면·처리·데이터
  - 코드 (한 줄 42자 이하):
    ```python
    q = st.text_input("질문")  # 화면: 입력
    if q:
        rows = search(q)       # 데이터: 조회
        ans = answer(q, rows)  # 처리: 규칙·모델
        st.write(ans)          # 화면: 결과
    ```
  - 캡션: 함수 이름은 가상 · 실제 실습 코드와 다를 수 있음
- 해석 항목:
  1. 화면: 입력을 받고 결과 표시
  2. 처리: 업무 규칙·모델 연결
  3. 데이터: 기사 본문·DB 조회
- 출처: Streamlit Architecture 문서 · Streamlit API 문서(st.text_input, st.write) · 근거: 사용자 제공 강의안
- 발표자 노트: 화면에서 입력을 받고, 규칙과 모델 호출로 처리하고, 데이터를 조회해 다시 화면에 보여 주는 전체 흐름을 다루는 것을 흔히 풀스택이라고 부릅니다. Streamlit에서는 이 흐름을 Python 코드 몇 줄로 이을 수 있어서, 왼쪽 예시처럼 입력 칸, 조회, 모델 호출, 결과 표시가 한 파일 안에 차례로 나옵니다. Streamlit은 Python 서버가 코드를 실행하고 브라우저는 화면을 보여 주는 구조라서, 오전 앱은 화면과 처리 사이에 별도 백엔드 서버를 두지 않았고 모델만 오전에 본 추론 서버에 API로 요청합니다. React나 별도 백엔드를 처음부터 모두 배우기보다, 지금 바꿀 부분이 화면인지, 처리인지, 데이터인지 알아보는 것부터 시작하면 AI가 만든 코드도 더 잘 판단할 수 있습니다. 앞 시간에 적은 개선 기능은 화면, 처리, 데이터 중 어디를 바꾸는 일인가요? 손가락으로 1, 2, 3을 표시해 주세요.
- 제작 메모: 코드는 실제 실습 코드가 아닌 표준 예시다. `st.text_input` 반환값을 `if`로 확인한 뒤 `st.write`로 표시하는 형태는 Context7 Streamlit 공식 문서 예시와 같다. `search`, `answer`는 가상 함수 이름이다. 주석은 27열에 맞췄고 한 줄 최대 38자(4줄)다. 해석 항목 2의 "업무 규칙·모델 연결"은 S24 표의 두 영역 이름을 그대로 써서 두 장면의 용어를 맞췄다.
- 체크리스트 대조: 13번 해당. 모델 이름·주소·키 없이 가상 함수 이름만 사용. 콘티 화면 구성 "별도 API 서버가 없는 구조에 임의로 서버를 추가하지 않는다"를 지키고, 노트에서 Streamlit 서버–브라우저 구조를 공식 문서 범위로 설명. research_claude 2절 "기술스택 공부는 필수이고 누구나 풀스택 개발 가능"을 "바꿀 부분의 역할부터 알면 AI가 만든 결과를 더 잘 판단"으로 바꿈. 콘티 항목 3 "데이터: 조회와 저장"은 오전 앱이 저장 기능을 가진다는 근거가 없어 "기사 본문·DB 조회"로 수정.
- 수정 기록(2026-09-14): W23 반영 — 노트 3문장 "오전 앱에는 별도 API 서버를 따로 두지 않았습니다"를 "오전 앱은 화면과 처리 사이에 별도 백엔드 서버를 두지 않았고 모델만 오전에 본 추론 서버에 API로 요청합니다"로 교체(B1 S06 모델 처리 위치와 충돌 제거, 사실 경계 4·11번). 노트 6문장 유지. 실제 실습 구조가 다르면 보류 3(강사 검토 Q7)에 따라 다시 맞춘다.

## S33 · 다른 입력으로 재확인

- 항목 (`.bullets`, 3개):
