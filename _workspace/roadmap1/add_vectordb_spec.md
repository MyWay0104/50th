## V01 · 벡터 저장소는 왜 필요한가 (data-skill `split` 또는 `compare`)

- 제목: "벡터 저장소는 왜 필요한가"
- thesis: "글자가 같은 것이 아니라 뜻이 가까운 것을 빨리 찾으려고 둡니다."
- explain(2~3문장): 키워드 검색은 같은 낱말이 있어야 찾지만, 뜻을 숫자 묶음(벡터)으로 바꿔 두면 표현이 달라도 가까운 조각을 찾을 수 있습니다. 조각이 수천·수만 개가 되면 하나하나 비교할 수 없어, 벡터를 저장하고 가까운 것을 빠르게 찾아 주는 전용 저장소를 둡니다. 오늘 실습은 기사 한 편이라 조각이 몇 개뿐이지만, 같은 구조를 씁니다.
- 시각: 왼쪽 비교 두 열 — "키워드 검색: '장비 고장' ↔ '설비 이상' 못 찾음" / "벡터 검색: 뜻이 가까워 찾음" (개념 예시, 수치 없음). 오른쪽 `.dg` 도식 — [조각들] → [뜻을 숫자로] → [벡터 저장소] → [질문과 가까운 것 몇 개] (검색 단계는 "나중에 쓰는 방식"이라는 캡션). 또는 "존재 목적 세 가지" 카드: 뜻으로 찾기 · 많아져도 빠르게 · 출처(메타데이터)와 함께 보관.
- 노트(5~6문장): 일반 DB는 값이 같은 행을 찾고, 벡터 저장소는 뜻이 가까운 조각을 찾는다는 차이. 조각 수가 적을 때는 그냥 리스트로도 되지만, 많아지면 전용 저장소가 필요. 오늘 실습에서는 저장까지만 손으로 하고 꺼내 쓰는 방식은 다음 장에서. 참여 질문: "우리 부서 문서가 만 건이라면 키워드 검색과 뜻 검색 중 무엇이 먼저 막힐까요?" 다음 장 예고: "실습에 나오는 FAISS와 자주 듣는 두 가지 이름을 비교".
- 출처: Lewis et al. 2020 · LangChain Vector stores 문서

## V02 · FAISS · Chroma · Milvus (data-skill `compare`, cols-3, A03 골격)

- 제목: "FAISS · Chroma · Milvus"
- thesis: "셋 다 벡터를 저장하고 가까운 것을 찾지만, 어디서 얼마나 크게 돌리느냐가 다릅니다."
- explain(2~3문장): FAISS는 Meta가 만든 검색 라이브러리로 내 프로그램 안(메모리)에서 바로 쓰고 파일로 저장할 수 있어 오늘 실습에 씁니다. Chroma는 설치가 간단한 오픈소스 벡터 DB로 로컬 프로젝트에 붙이기 쉽습니다. Milvus는 서버로 띄워 여러 사람·많은 자료를 다루는 규모용입니다. 우열이 아니라 규모와 운영 방식의 차이입니다.
- 세 열(각 kicker · heading · 항목 2개 · note):
  - "라이브러리 · 오늘 실습" FAISS — "프로그램 안에서 바로 검색" · "인덱스를 파일로 저장·불러오기" — note "서버 없음 · 개인 실습·소규모"
  - "가벼운 DB" Chroma — "설치 간단, 로컬에 저장" · "출처 같은 메타데이터 함께 보관" — note "작은 팀 프로젝트"
  - "서버형 DB" Milvus — "여러 사용자·대용량" · "분산·운영 기능" — note "사내 공용 서비스 규모"
- 아래 띠(`.dg-row.is-band`): "공통: 벡터 저장 + 가까운 것 찾기 · 다른 점: 규모·운영" / "실습 코드에서 저장소 이름은 실습 가이드 해당 장" — 개념 예시 배지.
- 노트(5~7문장): 세 이름을 처음 들으면 서로 다른 기술 같지만 하는 일은 같다. FAISS는 DB라기보다 검색 라이브러리라 서버가 없고 오늘처럼 노트북 안에서 쓰기 좋다. Chroma는 DB 형태로 로컬에 파일을 두고 메타데이터 필터가 편하다. Milvus는 서버를 따로 띄우며 사내 공용 규모에 쓴다(이번 교육 범위 밖). 실습 코드에서 FAISS를 다른 저장소로 바꿔도 앞 장의 구조(나누기→숫자로→저장→찾기)는 그대로. 참여 질문: "오늘 실습처럼 기사 한 편이면 셋 중 무엇이면 충분할까요?" 사실 경계: 성능 비교 수치를 말하지 않는다. "밀버스" 표기는 화면에서 "Milvus".
- 출처: FAISS 공식 문서(GitHub wiki) · Chroma 공식 문서 · Milvus 공식 문서
