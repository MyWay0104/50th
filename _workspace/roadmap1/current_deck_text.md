## 5쪽 · S03 · data-skill split

- 화면: AI·머신러닝·LLM의 관계 AI·머신러닝·딥러닝·LLM은 대체가 아니라 포함 관계입니다. AI 안에 머신러닝이, 그 안에 신경망을 쓰는 딥러닝이 있고, 현대 LLM은 주로 딥러닝 기반입니다. 오늘은 역사 전체가 아니라 문맥을 다루는 방식만 가져갑니다. AI · 넓은 분야 전체 머신러닝 · 데이터로 패턴을 학습 딥러닝 · 신경망으로 학습 LLM 개념 예시 · 포함 관계를 나타낸 그림 · 연표가 아님 앞 몇 단어만 N-gram 등 가까운 단어로 예측 → 순서대로 읽기 RNN·LSTM 등 먼 정보가 흐려짐 → 2017 Transformer 멀리 있는 단어도 직접 참고 언어 모델이 문맥을 다루는 방식의 변화 · 개념 예시 출처: Vaswani et al., Attention Is All You Need (2017)
- 노트: 화면의 네 용어는 앞의 기술이 뒤의 기술로 대체된 순서가 아니라 포함 관계로 보시면 됩니다. 화면 왼쪽 그림처럼 머신러닝은 데이터로 패턴을 학습하고, 딥러닝은 그중 신경망을 쓰는 방법이며, 현대 LLM은 주로 딥러닝 기반입니다. 오른쪽은 언어 모델이 문맥을 다뤄 온 방식의 변화로, 바로 앞 몇 단어만 보던 방식에서 순서대로 읽는 방식을 거쳐 2017년 Transformer가 멀리 떨어진 단어도 직접 참고하게 만들었습니다. 오늘은 역사 전체보다 문맥을 다루는 방식이 바뀌었다는 점만 기억하시면 됩니다. 분류, 요약, 코드 생성 중 내 업무와 가까운 작업을 하나 마음속으로 골라 두세요.

## 6쪽 · S04 · data-skill steps

- 화면: LLM의 응답 생성 LLM은 사실을 조회하지 않고 다음 토큰의 확률 분포를 계산합니다. 보통의 호출은 학습된 모델로 계산만 하므로, 질문을 더 보낸다고 모델이 재학습되지 않습니다. 다음 실습에서 바꿀 temperature 값은 3단계의 선택에 영향을 줍니다. 1 토큰으로 나누기 회의 | 내용을 | 세 | 줄로 2 다음 토큰 분포 계산 후보: 요약 · 정리 · … 3 선택하고 반복 '요약'을 골라 뒤에 붙임 고른 토큰을 입력 끝에 붙여 2단계로 돌아가기 — 답이 끝나거나 길이 한도에 닿을 때까지 반복 개념 예시 · 실제 토큰 분할은 모델마다 다름 · 확률 수치 없음 출처: Vaswani et al. 2017 · Ouyang et al. 2022 (지시 수행 학습)
- 노트: LLM은 입력을 토큰이라는 단위로 나누고, 지금까지의 문맥으로 다음 토큰 후보들의 가능성을 계산해 하나를 고르는 과정을 반복합니다. 화면의 세 카드 아래 줄처럼, 고른 토큰을 입력 끝에 붙여 다시 2단계로 돌아가는 방식을 자기회귀 생성이라고 합니다. 토큰은 단어 하나와 항상 같지 않고, 나누는 방식은 모델마다 다릅니다. 학습 단계에서는 모델 매개변수를 바꾸지만, 오늘 우리가 하는 API 호출은 이미 학습된 모델로 결과를 계산할 뿐입니다. 토큰 수는 비용과 속도, 한 번에 넣을 수 있는 입력 길이를 재는 단위이기도 합니다. 그러면 재학습이 아닌데도 같은 질문의 답이 달라진다면, 세 단계 중 어디에서 갈리는지 한 분만 답해 주세요.

## 7쪽 · S05 · data-skill split

- 화면: Attention과 문맥 Attention은 다른 위치의 정보를 얼마나 반영할지 계산하는 장치입니다. 오른쪽 그림의 주황색 Attention 칸이 이 계산을 합니다. 원 논문은 번역용 encoder–decoder 구조이고, 오늘날 많은 생성 모델은 decoder 중심입니다. 개념 예시 같은 '배', 다른 문맥 디저트로 배를 먹었다 → 배 = 과일 항구에서 배를 탔다 → 배 = 선박 밑줄 친 말: 참고하는 주변 단어 · 개념 예시 · 측정값 아님 Vaswani et al. (2017), Figure 1 · arXiv:1706.03762 왼쪽 묶음 · encoder 입력을 읽는 쪽 오른쪽 묶음 · decoder 출력을 만드는 쪽 출처: Vaswani et al. 2017
- 노트: 같은 '배'라도 '먹었다'와 함께 오면 과일, '탔다'와 함께 오면 선박으로 읽힙니다. Attention은 각 위치의 표현을 만들 때 다른 위치의 정보를 얼마나 반영할지 계산하는 장치이고, 이 값은 입력마다 새로 계산되므로 학습된 모델 매개변수와는 다릅니다. 화면 오른쪽은 원 논문의 전체 구조 그림으로, 왼쪽 묶음이 입력을 읽는 encoder, 오른쪽 묶음이 출력을 만드는 decoder이고, 주황색 Multi-Head Attention 칸이 방금 말한 계산을 하는 곳입니다. 원 논문은 번역용 encoder–decoder 구조였고, 오늘날 많은 생성 모델은 decoder 중심 구조를 씁니다. 데이터·규모·학습 방법이 발전하며 쓰임이 넓어졌지만, 이를 어느 한순간에 갑자기 달라진 일로 단정하지는 않겠습니다. Multi-Head 구조와 Q·K·V 계산은 부록의 Transformer 장면에서 더 자세히 다루니, 궁금한 분은 쉬는 시간에 보셔도 됩니다.

## 8쪽 · S06 · data-skill split

- 화면: 모델·서버·API의 역할 코드는 내 PC에서 돌고, 모델 계산은 서버에서 합니다. API는 요청·응답 형식의 약속, SDK·LangChain 같은 Python 라이브러리는 그 호출을 돕습니다. 코드에 OpenAI라는 이름이 있어도 요청은 base_url에 적은 서버로 갑니다. 개념 예시 내 PC 실습 코드 라이브러리로 요청 작성 ⇄ API 요청·응답 사내 서버 추론 서버 vLLM → 모델 주소·모델명·키 대신 역할 이름으로 표시 요청 목적지를 정하는 곳 · 개념 예시 from langchain_openai import ChatOpenAI llm = ChatOpenAI( model=MODEL , # 사용할 모델 이름 base_url=BASE_URL , # 요청을 받을 서버 주소 ) # 키는 환경변수에서 읽음 코드 위치: 모델 연결 설정 — 실습 가이드 해당 장 출처: vLLM Online Serving 문서 · LangChain Models 문서
- 노트: 모델은 응답을 계산하는 핵심이고, vLLM은 요청을 받아 모델을 실행하는 서버 프로그램입니다. API는 프로그램끼리 요청과 응답을 주고받는 약속이고, SDK나 LangChain은 그 호출 코드를 편하게 쓰게 돕는 Python 도구이고, 오른쪽 코드는 LangChain으로 쓴 것입니다. 화면 왼쪽 그림처럼 코드는 내 PC에서 돌아도 모델 계산은 사내 서버에서 일어나고, 그 요청이 어디로 갈지는 오른쪽 코드의 base_url이 정합니다. 그래서 코드에 OpenAI라는 이름이 있어도 요청이 OpenAI로 가는 것은 아니고, 호환 API라고 해서 모든 옵션과 도구 호출이 똑같이 지원되는 것도 아닙니다. 코드 첫 줄의 langchain은 다음 RAG 구간에서 다루니, 지금은 model과 base_url 두 줄만 보세요. 이제 실습 가이드 해당 장의 모델 연결 설정에서 모델 이름과 요청 주소를 지정하는 위치를 같이 보겠습니다.

- 노트: 오전에 LangChain으로 모델과 검색을 연결했다면, LangGraph는 코드 안에 숨어 있던 흐름을 눈에 보이는 그래프로 밖으로 꺼내는 도구입니다. 화면 왼쪽 그림처럼 모든 노드가 같은 State를 읽고 일부를 갱신하며, 분류 노드 뒤의 조건부 Edge가 질문 종류에 따라 다음 노드를 고릅니다. 분기 예시는 오전에 본 기사 검색과 SQL 조회를 빌려 온 것일 뿐, 오전 앱이 이렇게 만들어졌다는 뜻은 아닙니다. create_agent가 만드는 도구 호출 루프도 안을 보면 모델 노드와 도구 노드가 조건부 Edge로 오가는 그래프입니다. 오른쪽 코드는 그래프를 만들고, 노드를 붙이고, Edge로 잇고, compile한 뒤 실행하는 순서를 교육용으로 줄인 것이고, 체크포인터를 붙이면 중단한 지점에서 이어갈 수 있습니다. 순차 연결, 라우팅, 병렬, 오케스트레이터-워커, 평가-개선 같은 워크플로 패턴도 모두 이 세 요소로 그릴 수 있고, 되돌아가는 루프에는 반드시 멈추는 조건을 둡니다. 순서가 고정된 작업이라면 함수 호출만으로도 충분하니, 분기·중단·재개가 정말 필요한지부터 확인하세요.

## 55쪽 · A08 · data-skill steps

- 화면: 부록 · Agentic RAG 검색 결과를 평가해 부족하면 질문을 고쳐 다시 찾습니다. 앞의 RAG 구간에서 본 '검색이 틀렸나' 확인을 그래프에 넣은 구조입니다. 모델이 문서마다 관련성을 yes/no로 매기고, 그 결과로 경로가 갈립니다. 판정마다 호출이 늘어 재시도 횟수를 제한합니다. 검색 retrieve → 관련성 평가 문서별 yes/no → yes 답변 생성 generate ↓ no 질문 재작성 다시 검색으로 · 횟수 제한 개념 예시 관련성 판정 스키마 · 교육용 축약(일부 줄 생략) class GradeDocuments(BaseModel): score: Literal["yes", "no"] grader = model.with_structured_output( GradeDocuments) grade = grader.invoke(prompt).score 출처: LangGraph Agentic RAG 문서 · Lewis et al. 2020
- 노트: 앞의 RAG 구간에서 답이 틀리면 검색이 틀렸는지, 가져온 자료를 잘못 설명했는지부터 나눠 보자고 했는데, Agentic RAG는 그 판단의 일부를 그래프 안에 넣은 구조입니다. 화면 왼쪽 그림처럼 검색한 뒤 모델이 문서마다 질문과 관련 있는지 yes나 no로 판정하고, 관련 문서가 있으면 답변을 만들고 없으면 질문을 고쳐 다시 검색합니다. 오른쪽 코드는 그 판정을 정해진 형식으로 받도록 yes와 no 두 값만 허용하는 스키마를 모델에 연결하는 부분을 교육용으로 줄인 것입니다. 이 그림에서 모델이 하는 일은 관련성 판정이고, 어느 길로 갈지는 그 결과를 받은 조건부 Edge가 정한다는 점도 봐 두세요. 같은 계열인 Corrective RAG는 근거가 부족하면 웹 검색으로 보완하고, Self-RAG는 답변이 근거에 맞는지까지 평가하며, Adaptive RAG는 질문에 따라 검색을 안 할지, 한 번 할지, 여러 번 할지를 먼저 고르는데, 사내망에서는 웹 검색 자체를 쓸 수 없을 수도 있습니다. 판정 한 번마다 모델 호출이 늘어 시간과 비용이 커지므로 재검색 횟수에 상한을 두고, 상한에 닿으면 억지로 답하지 않고 근거를 찾지 못했다고 알리게 합니다. 평가 단계를 넣었다고 환각이 사라지는 것은 아니니 근거 확인은 계속 필요합니다. 오늘 실습한 기본 RAG로 충분한지부터 확인하세요.

## 56쪽 · A09 · data-skill split

- 화면: 부록 · 하네스와 Deep Agents 하네스는 모델에 도구·기억·맥락을 묶는 실행 틀입니다. Deep Agents는 LangGraph 위에 계획·파일·위임 등을 미리 묶은 하네스입니다. Claude Code도 구현은 다르지만 같은 역할의 실행 틀입니다. 짧은 도구 호출이면 create_agent로 충분합니다. 하네스 · 모델을 둘러싼 실행 틀 모델 Tools 외부 기능 Memory 상태·저장소 Context 지침·규칙 Deep Agents가 미리 묶은 것 작업 계획 파일 도구 긴 출력 보관 하위 작업 개념 예시 create_deep_agent 인자 · 교육용 축약(값 생략) agent = create_deep_agent( model=..., tools=[...], subagents=[...], skills=[...], backend=..., interrupt_on={...}, ) 출처: LangChain Concepts(Agent harnesses: Deep Agents)
- 노트: 오후 실습에서 Claude Code가 파일을 읽고, 계획을 세우고, 명령을 실행하는 모습을 보셨는데, 이것은 모델 혼자 하는 일이 아니라 모델을 둘러싼 실행 틀이 해 주는 일이고, 이 틀을 하네스라고 부릅니다. 화면 왼쪽 그림처럼 하네스는 모델에 외부 기능을 부르는 Tools, 대화와 기록을 남기는 Memory, 지침과 규칙을 담는 Context를 묶습니다. Memory는 대화 중 상태를 저장하는 체크포인터와 대화를 넘어 남기는 저장소로 나뉘고, Context에는 모델 호출 앞뒤에서 로그를 남기거나 가드레일을 거는 미들웨어가 들어갑니다. Deep Agents는 LangGraph 위에 작업 계획 목록, 허용된 경로 안의 파일 도구, 긴 출력을 파일로 넘기는 오프로딩, 하위 작업 위임을 미리 묶어 둔 하네스이고, 오른쪽 코드는 그 설정의 인자 이름만 보여 주며 값은 생략했습니다. Claude Code도 하네스라고 했지만 LangGraph나 Deep Agents로 만든 것은 아니고, 모델을 둘러싼 실행 틀이라는 역할이 같다는 뜻입니다. 다음 장에서 볼 사내 배포 패키지 예시도 이런 구성으로 만든 참고 예시입니다. 다만 도구 몇 개를 짧게 호출하는 작업이라면 create_agent로 충분하고, 하네스 기능은 긴 작업, 파일 작업, 사람 승인 같은 요구가 생길 때 고르면 됩니다. 인자 이름은 설치 판본에 따라 달라질 수 있으니 공식 문서에서 확인하세요.

## 57쪽 · A10 · data-skill steps

- 화면: 부록 · 사람 승인(HITL) 되돌리기 어려운 도구 실행 전에 멈추고 사람의 결정으로 재개합니다. interrupt()로 멈추고 Command(resume)로 사람의 결정을 받아 이어갑니다. 멈춘 상태를 저장할 체크포인터가 필요합니다. CLAUDE.md나 프롬프트의 '하지 마' 문장은 이것을 대신하지 못합니다. 도구 호출 모델이 요청 → 멈춤 interrupt() → 사람 결정 resume로 재개 ↓ 승인 도구 실행 거부 사유를 모델에 지정한 도구만 멈춤 · 결과는 다시 모델로 · 개념 예시 사내 배포 패키지 예시 화면의 승인 카드 · 실행할 명령과 승인·거부 버튼 · 수강생 실습 화면 아님 출처: LangGraph Human-in-the-loop 문서
- 노트: 삭제, 셸 실행, 외부 시스템 변경처럼 되돌리기 어려운 행동은 모델이 요청하더라도 사람이 한 번 보고 결정하게 하는 것이 안전합니다. 화면 왼쪽 그림처럼 모델이 도구 호출을 요청하면 interrupt()로 그래프를 멈추고, 사람이 승인하면 도구를 실행하고, 거부하면 그 사유를 모델에게 돌려줍니다. 사람의 결정은 Command(resume)로 전달해 멈춘 곳부터 이어가는데, 멈춘 상태를 저장해 둘 체크포인터가 있어야 하고, 저장된 상태는 나중에 조회해 어느 시점에서 멈췄는지 확인할 수도 있습니다. 앞 장 코드의 interrupt_on처럼 Deep Agents에서는 어떤 도구 앞에서 멈출지 설정으로 선언만 해도 같은 효과를 냅니다. 오른쪽 화면은 사내 배포 패키지 예시로, 셸 명령을 실행하기 전에 도구 이름과 명령을 보여 주고 승인과 거부를 받는 장면입니다. 수강생 실습 화면은 아니고, 승인 카드 부분만 잘라 보여 드립니다. 오후 실습에서 Claude Code가 파일 수정이나 명령 실행 전에 승인을 요청했다면 그것도 같은 발상의 장치이고, CLAUDE.md나 프롬프트에 "하지 마"라고 적는 문장은 이런 멈춤 장치를 대신하지 못합니다.
