제가 앱을 만들 때 개발 후반으로 갈수록 작은 수정 하나가 여러 곳에 영향을 줘서 고치기 어려워진 경험이 있습니다. 그래서 처음부터 완벽한 구조를 목표로 하기보다, 바뀌기 쉬운 부분의 경계와 각 부분이 주고받는 값을 먼저 정해 두는 편이 낫다고 봅니다. 왼쪽 그림은 오전 마지막에 본 세 층 그림을 역할 이름으로 다시 그린 것입니다. 오전 그림의 모델·도구 층 중 모델 연결과 업무 규칙은 처리로, 검색·SQL 조회는 데이터를 꺼내는 입구라 데이터 쪽으로 옮겨 읽습니다. 검색 결과 없음 안내는 주황 점선 안의 화면과 처리 중 업무 규칙만 바꾸고, 모델 연결은 그대로 두며, 데이터 쪽은 빈 결과가 어떤 형태로 오는지만 확인하면 됩니다. 이렇게 경계가 보이면 Claude Code에 요청할 때도 바꿀 곳과 건드리지 않을 곳을 말할 수 있고, 공식 모범사례도 요청에 관련 파일과 제약을 구체적으로 적으라고 권합니다. 작은 앱이라면 파일을 많이 나눌 필요 없이 역할별 함수 몇 개와 짧은 README로 충분합니다. 그러면 "근거 문단을 답변 옆에 함께 보여 주기"는 세 층 중 어디를 바꿔야 할까요? 한 분만 답해 주세요.
