채팅용 키로는 임베딩 모델의 문이 열리지 않습니다
실습 환경은 세 층으로 기억하시면 됩니다. 코드는 내 PC에서 돌고, 모델은 사내 LLM 게이트웨이 뒤에서 돕니다. 그 둘을 잇는 것이 환경 파일에 적는 주소와 열쇠입니다. 문은 게이트웨이에 달려 있고, 그 뒤에 모델이 있습니다. 열쇠는 세 개입니다. 채팅용 키와 임베딩용 키는 둘 다 사내 모델 운영 페이지에서 받지만, 채팅용 키로는 임베딩 모델의 문이 열리지 않아서 따로 받습니다. 임베딩은 글의 뜻을 숫자로 바꾸는 일이고 RAG 실습에서 설명합니다. 셋째 열쇠인 데이터 조회용 토큰은 게이트웨이 밖, 다른 플랫폼의 문을 여는 열쇠입니다. 지금은 받지 않고 Tool 실습에서 받으며, 시간이 지나면 만료됩니다. 첫째 열쇠는 오후에 Claude Code를 연결할 때 그대로 다시 쓰니 잘 챙겨 두세요. 질문 하나 드리겠습니다. 환경 파일의 채팅용 키 칸이 비어 있으면 세 층 가운데 어디에서 막힐까요? 그러면 열쇠 두 개를 받아 첫 응답까지 직접 가 보겠습니다.

LLM은 두뇌입니다. 판단하고 설명하지만 아직 손발이 없습니다.

오늘의 첫 정거장은 두뇌입니다. LLM은 두뇌라서 판단하고 설명하지만, 아직 손발이 없어서 물어보면 대답만 합니다. 용어를 먼저 정리하면, AI 안에 데이터로 패턴을 학습하는 머신러닝이 있고 그 안에 신경망을 쓰는 딥러닝이 있으며, 오늘 다루는 LLM은 딥러닝 기반의 언어 모델입니다. 대체 관계가 아니라 포함 관계이고, 오늘은 그중 LLM이 답을 만드는 방식만 가져갑니다. LLM은 입력을 토큰이라는 단위로 나누고, 지금까지의 문맥으로 다음 토큰 후보들의 가능성을 계산해 하나를 고르는 과정을 반복합니다. 화면의 세 카드 아래 줄처럼, 고른 토큰을 입력 끝에 붙여 다시 2단계로 돌아가는 방식을 자기회귀 생성이라고 합니다. 토큰은 단어 하나와 항상 같지 않고, 나누는 방식은 모델마다 다릅니다. 학습 단계에서는 모델 매개변수를 바꾸지만, 오늘 우리가 하는 호출은 이미 학습된 모델로 결과를 계산할 뿐입니다. 토큰 수는 비용과 속도를 재는 단위이면서, 한 번에 넣을 수 있는 입력과 출력 길이의 한도인 컨텍스트 윈도우를 재는 단위이기도 합니다. 이 한도는 RAG 구간에서 자료를 나누는 첫 이유로 다시 나옵니다. Attention이 문맥을 어떻게 모으는지는 부록에 한 장 있으니 궁금한 분은 나중에 보세요. 그러면 재학습이 아닌데도 같은 질문의 답이 달라진다면, 세 단계 중 어디에서 갈리는지 한 분만 답해 주세요. 갈리는 곳은 3단계, 고르는 단계입니다. 그 폭을 정하는 값이 temperature이고 첫 질문 실습 뒤에 직접 바꿔 봅니다. 이어서 이 두뇌에게 질문을 보내는 코드가 어떤 모양인지 보겠습니다.

ReAct 논문은 판단을 '생각'이라고 부릅니다. 판단은 기록에 따로 찍히지 않을 수 있는데, 어느 도구를 어떤 값으로 부르자는 호출 요청이 판단의 결과입니다. 호출 요청이 없으면 끝납니다. 다만 끝나지 않고 계속 돌 수도 있습니다. 그래서 맡기는 만큼 멈춤 장치를 함께 둡니다. 코드에는 max_iterations라는 이름으로 적혀 있고, 이어지는 실습의 웹 화면판에는 5회로 걸려 있습니다. 표지에서 드린 질문의 답이 여기 있습니다. 상한을 올려도 답은 좋아지지 않습니다. 멈추게 하는 값이기 때문입니다. 프롬프트에 위험한 조회는 하지 말라고 적는 것은 지침일 뿐 막는 장치가 아닙니다. 그래서 도구에 넣는 값은 조회문을 바꾸지 못하게 코드가 처리합니다. 조회만 허용하는 권한은 오늘 실습 코드 이야기가 아니라 업무에 옮길 때의 일반 원칙이고, 사람이 승인하는 방법과 함께 부록에 두었습니다. 이 Agent를 동료도 쓸 수 있게 화면에 올립니다. 먼저 그 화면의 구조를 보겠습니다.

부록 · Transformer와 Q·K·V

Attention은 Q·K 비교로 정한 비율대로 V를 모읍니다.

비율은 입력마다 새로 계산되는 값이며 학습된 매개변수와 다릅니다. 원 논문은 encoder–decoder 구조이고, 많은 생성 모델은 decoder 중심입니다.

  • Q·K·V 찾는 기준·이름표·내용비유 · 한 토큰 표현에서 나온 세 벡터
  • 그림 왼쪽: 헤드 하나의 계산softmax(QKT / √d) · V
  • 그림 오른쪽: 여러 헤드를 나란히헤드 = Q·K·V 계산 한 벌 · 헤드마다 다른 변환

Vaswani et al. (2017), Figure 2 · arXiv:1706.03762

출처: Vaswani et al., Attention Is All You Need (2017) · arXiv:1706.03762

오전 응답 생성 장면에서 모델이 문맥을 보고 다음 토큰을 고른다고 했는데, 그 문맥을 반영하는 계산이 Attention이고 그 재료가 Q·K·V이며, 비유하면 Q는 찾는 기준, K는 비교될 이름표, V는 실제로 전달할 내용입니다. 화면 오른쪽 원 논문 그림 중 왼쪽이 헤드 하나의 계산으로, 아래에서부터 Q와 K를 곱해 비교하고 크기를 조정한 뒤 softmax로 반영 비율을 만들어 그 비율대로 V를 모읍니다. 중간의 Mask는 선택 단계인데, 생성 모델은 이것으로 아직 나오지 않은 뒤쪽 토큰을 가립니다. 오른쪽 그림은 서로 다른 변환을 가진 여러 헤드가 이 계산을 나란히 한 뒤 이어 붙이는 구조이고, 실제 모델은 이것을 여러 층에서 반복합니다. 이 비율은 입력마다 새로 계산되는 값이라 학습된 매개변수와 다르며, 그림은 구조도이지 가중치를 측정한 결과가 아닙니다. 원 논문은 번역을 위해 encoder와 decoder를 함께 썼고, 오늘날 많은 생성 모델은 앞쪽 토큰만 참고하도록 가린 decoder 중심 구조를 씁니다. 원 논문 이후 여러 공개 모델은 RMSNorm, SwiGLU, RoPE 같은 변형을 쓰지만, Q·K 비교로 비율을 정해 V를 모으는 원리는 같습니다.

RAG 품질은 재학습이 아니라 분할·검색·메타데이터로 다듬습니다.

LangChain, LangGraph, Deep Agents는 차례로 모두 배워야 하는 과정이 아니라, 문제에 필요한 추상화 수준에 따라 고르는 선택지입니다. 단순 호출 하나라면 SDK만으로 되고, 오전 실습처럼 모델 호출과 자료·조회 도구를 잇는 정도라면 LangChain으로 충분한데, 오전 실습 코드의 langchain이 바로 그 연결 역할이고 코드가 짧다고 성능이 좋아지는 것은 아닙니다. 화면 아래 띠처럼 LangChain의 create_agent와 Deep Agents는 모두 LangGraph 실행 기반 위에서 동작하므로, 단계와 분기를 직접 정하거나, 상태를 저장했다가 중단한 곳에서 이어가거나, 사람 확인 단계를 넣어야 할 때 LangGraph를 직접 씁니다. Deep Agents는 그 위에 계획, 파일 공간, 하위 작업 위임을 미리 묶어 둔 하네스로, 여러 단계로 이어지는 긴 작업에 맞춰져 있습니다. 예제 코드 길이가 다르다고 성능이 다른 것은 아니며, 같은 과제로 비교한 결과가 아니면 성능 비교로 읽지 않습니다. 여러 Agent를 감독자형이나 넘겨주기형으로 나누는 방식도 있는데, 이것 역시 Agent 하나로 충분한지 먼저 확인한 뒤 고릅니다. LangGraph와 Deep Agents는 뒤의 부록 장에서 하나씩 더 보겠습니다.

검색 결과를 평가해 부족하면 질문을 고쳐 다시 찾습니다.

앞의 RAG 구간에서 답이 틀리면 검색이 틀렸는지, 가져온 자료를 잘못 설명했는지부터 나눠 보자고 했는데, Agentic RAG는 그 판단의 일부를 그래프 안에 넣은 구조입니다. 화면 왼쪽 그림처럼 검색한 뒤 모델이 문서마다 질문과 관련 있는지 yes나 no로 판정하고, 관련 문서가 있으면 답변을 만들고 없으면 질문을 고쳐 다시 검색합니다. 오른쪽 코드는 그 판정을 정해진 형식으로 받도록 yes와 no 두 값만 허용하는 스키마를 모델에 연결하는 부분을 교육용으로 줄인 것입니다. 이 그림에서 모델이 하는 일은 관련성 판정이고, 어느 길로 갈지는 그 결과를 받은 조건부 Edge가 정한다는 점도 봐 두세요. 같은 계열인 Corrective RAG는 근거가 부족하면 웹 검색으로 보완하고, Self-RAG는 답변이 근거에 맞는지까지 평가하며, Adaptive RAG는 질문에 따라 검색을 안 할지, 한 번 할지, 여러 번 할지를 먼저 고르는데, 사내망에서는 웹 검색 자체를 쓸 수 없을 수도 있습니다. 판정 한 번마다 모델 호출이 늘어 시간과 비용이 커지므로 재검색 횟수에 상한을 두고, 상한에 닿으면 억지로 답하지 않고 근거를 찾지 못했다고 알리게 합니다. 평가 단계를 넣었다고 환각이 사라지는 것은 아니니 근거 확인은 계속 필요합니다. 오늘 실습한 기본 RAG로 충분한지부터 확인하세요.

삭제, 셸 실행, 외부 시스템 변경처럼 되돌리기 어려운 행동은 모델이 요청하더라도 사람이 한 번 보고 결정하게 하는 것이 안전합니다. 화면 왼쪽 그림처럼 모델이 도구 호출을 요청하면 interrupt()로 그래프를 멈추고, 사람이 승인하면 도구를 실행하고, 거부하면 그 사유를 모델에게 돌려줍니다. 사람의 결정은 Command(resume)로 전달해 멈춘 곳부터 이어가는데, 멈춘 상태를 저장해 둘 체크포인터가 있어야 하고, 저장된 상태는 나중에 조회해 어느 시점에서 멈췄는지 확인할 수도 있습니다. 앞 장 코드의 interrupt_on처럼 Deep Agents에서는 어떤 도구 앞에서 멈출지 설정으로 선언만 해도 같은 효과를 냅니다. 오른쪽 화면은 사내 배포 패키지 예시로, 셸 명령을 실행하기 전에 도구 이름과 명령을 보여 주고 승인과 거부를 받는 장면입니다. 수강생 실습 화면은 아니고, 승인 카드 부분만 잘라 보여 드립니다. 오후 실습에서 Claude Code가 파일 수정이나 명령 실행 전에 승인을 요청했다면 그것도 같은 발상의 장치이고, CLAUDE.md나 프롬프트에 "하지 마"라고 적는 문장은 이런 멈춤 장치를 대신하지 못합니다.
