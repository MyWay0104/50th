AI·머신러닝·LLM의 관계

AI·머신러닝·딥러닝·LLM은 대체가 아니라 포함 관계입니다.

LLM의 응답 생성

LLM은 사실을 조회하지 않고 다음 토큰의 확률 분포를 계산합니다.

보통의 호출은 학습된 모델로 계산만 하므로, 질문을 더 보낸다고 모델이 재학습되지 않습니다. 다음 실습에서 바꿀 temperature 값은 3단계의 선택에 영향을 줍니다.

  1. 1
    토큰으로 나누기회의 | 내용을 | 세 | 줄로
  2. 2
    다음 토큰 분포 계산후보: 요약 · 정리 · …
  3. 3
    선택하고 반복'요약'을 골라 뒤에 붙임
고른 토큰을 입력 끝에 붙여 2단계로 돌아가기 — 답이 끝나거나 길이 한도에 닿을 때까지 반복

개념 예시 · 실제 토큰 분할은 모델마다 다름 · 확률 수치 없음

출처: Vaswani et al. 2017 · Ouyang et al. 2022 (지시 수행 학습)

LLM은 입력을 토큰이라는 단위로 나누고, 지금까지의 문맥으로 다음 토큰 후보들의 가능성을 계산해 하나를 고르는 과정을 반복합니다. 화면의 세 카드 아래 줄처럼, 고른 토큰을 입력 끝에 붙여 다시 2단계로 돌아가는 방식을 자기회귀 생성이라고 합니다. 토큰은 단어 하나와 항상 같지 않고, 나누는 방식은 모델마다 다릅니다. 학습 단계에서는 모델 매개변수를 바꾸지만, 오늘 우리가 하는 API 호출은 이미 학습된 모델로 결과를 계산할 뿐입니다. 토큰 수는 비용과 속도, 한 번에 넣을 수 있는 입력 길이를 재는 단위이기도 합니다. 그러면 재학습이 아닌데도 같은 질문의 답이 달라진다면, 세 단계 중 어디에서 갈리는지 한 분만 답해 주세요.

Attention과 문맥

Attention은 다른 위치의 정보를 얼마나 반영할지 계산하는 장치입니다.

오른쪽 그림의 주황색 Attention 칸이 이 계산을 합니다. 원 논문은 번역용 encoder–decoder 구조이고, 오늘날 많은 생성 모델은 decoder 중심입니다.

개념 예시
같은 '배', 다른 문맥
디저트로 배를 먹었다
→
배 = 과일
항구에서 배를 탔다
→
배 = 선박

밑줄 친 말: 참고하는 주변 단어 · 개념 예시 · 측정값 아님

Vaswani et al. (2017), Figure 1 · arXiv:1706.03762

왼쪽 묶음 · encoder입력을 읽는 쪽
오른쪽 묶음 · decoder출력을 만드는 쪽

출처: Vaswani et al. 2017

같은 '배'라도 '먹었다'와 함께 오면 과일, '탔다'와 함께 오면 선박으로 읽힙니다. Attention은 각 위치의 표현을 만들 때 다른 위치의 정보를 얼마나 반영할지 계산하는 장치이고, 이 값은 입력마다 새로 계산되므로 학습된 모델 매개변수와는 다릅니다. 화면 오른쪽은 원 논문의 전체 구조 그림으로, 왼쪽 묶음이 입력을 읽는 encoder, 오른쪽 묶음이 출력을 만드는 decoder이고, 주황색 Multi-Head Attention 칸이 방금 말한 계산을 하는 곳입니다. 원 논문은 번역용 encoder–decoder 구조였고, 오늘날 많은 생성 모델은 decoder 중심 구조를 씁니다. 데이터·규모·학습 방법이 발전하며 쓰임이 넓어졌지만, 이를 어느 한순간에 갑자기 달라진 일로 단정하지는 않겠습니다. Multi-Head 구조와 Q·K·V 계산은 부록의 Transformer 장면에서 더 자세히 다루니, 궁금한 분은 쉬는 시간에 보셔도 됩니다.

모델·서버·API의 역할

코드는 내 PC에서 돌고, 모델 계산은 서버에서 합니다.

API는 요청·응답 형식의 약속, SDK·LangChain 같은 Python 라이브러리는 그 호출을 돕습니다. 코드에 OpenAI라는 이름이 있어도 요청은 base_url에 적은 서버로 갑니다.

모델은 응답을 계산하는 핵심이고, vLLM은 요청을 받아 모델을 실행하는 서버 프로그램입니다. API는 프로그램끼리 요청과 응답을 주고받는 약속이고, SDK나 LangChain은 그 호출 코드를 편하게 쓰게 돕는 Python 도구이고, 오른쪽 코드는 LangChain으로 쓴 것입니다. 화면 왼쪽 그림처럼 코드는 내 PC에서 돌아도 모델 계산은 사내 서버에서 일어나고, 그 요청이 어디로 갈지는 오른쪽 코드의 base_url이 정합니다. 그래서 코드에 OpenAI라는 이름이 있어도 요청이 OpenAI로 가는 것은 아니고, 호환 API라고 해서 모든 옵션과 도구 호출이 똑같이 지원되는 것도 아닙니다. 코드 첫 줄의 langchain은 다음 RAG 구간에서 다루니, 지금은 model과 base_url 두 줄만 보세요. 이제 실습 가이드 해당 장의 모델 연결 설정에서 모델 이름과 요청 주소를 지정하는 위치를 같이 보겠습니다.

RAG의 기본 구조

미리 준비하는 인덱싱과 질문할 때의 검색·답변, 두 시점이 있습니다.

LangChain의 역할

LangChain은 연결을 표준화할 뿐, 모델을 똑똑하게 만들지 않습니다.

두 코드는 같은 요청을 같은 서버로 보냅니다. 이번 실습은 검색 결과를 모델 호출에 잇는 부분에 LangChain을 쓰며, 단순 호출이면 SDK로 충분합니다.

from openai import OpenAI
client = OpenAI(base_url=BASE_URL)
msgs = [{"role": "user", "content": prompt}]
res = client.chat.completions.create(
    model=MODEL, messages=msgs)
print(res.choices[0].message.content)
from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model=MODEL,
                 base_url=BASE_URL)
res = llm.invoke(prompt)
print(res.content)

LangChain의 장점은 모델, 메시지, 검색기, 도구를 같은 방식으로 연결하게 해 준다는 데 있고, 모델을 더 똑똑하게 만들어 주지는 않습니다. 화면 아래 띠는 세 도구를 제어 수준이라는 한 축으로 놓아 본 것인데, 오른쪽으로 갈수록 좋은 것이 아니라 흐름을 얼마나 직접 제어하느냐의 차이입니다. LangGraph는 흐름을 직접 설계해야 할 때, Deep Agents는 계획·파일·위임이 미리 묶인 틀로 긴 작업을 맡길 때 고르는 선택지라서, 순서대로 다 배울 필요 없이 부록의 프레임워크 선택 장면에 두었습니다. 실습 코드에서 질문, 검색 결과, 모델 응답이 각각 어디 있는지 짚어 보세요.

답변과 검색 근거 확인

틀렸다면 검색이 틀렸는지, 근거를 잘못 설명했는지부터 나눕니다.

도구(Tool) 호출 순서

모델은 도구 호출을 요청하고, 실행은 프로그램이 합니다.

프로그램이 도구의 이름·설명·입력 형식을 알려 주면 모델은 쓸 도구와 인자를 돌려줍니다. @tool은 함수 설명문(docstring)을 도구 설명으로 쓰므로, 설명이 모호하면 도구를 잘못 고릅니다.

  1. ① 프로그램
    도구 알려주기이름·설명·형식
  2. ② 모델
    호출 요청tool_calls
  3. ③ 프로그램
    실행과 반환조회 결과
  4. ④ 모델
    결과로 응답답변·다음 요청
@tool  # 교육용 가상 함수
def count_by_equipment(days: int) -> list:
    """최근 days일의 장비별 점검 건수"""

"모델이 도구를 쓴다"는 말은 모델이 Python 함수를 자기 안에서 실행한다는 뜻이 아닙니다. 화면 네 카드의 위쪽 라벨은 그 단계를 누가 하는지, 카드 아래 작은 줄은 각 단계에서 오가는 내용입니다. LangChain 코드에서는 각 단계를 도구 스키마, tool_calls, ToolMessage, AIMessage라는 이름으로 부릅니다. 프로그램이 도구 스키마를 알려 주면 모델은 tool_calls에 도구 이름과 인자, 예를 들어 days=7을 담아 요청만 하고, 실제 함수나 SQL은 프로그램이 실행해 결과를 ToolMessage로 돌려주면 모델이 답하거나 필요하면 다음 도구를 요청합니다. 아래 코드처럼 @tool은 함수 이름, docstring, 타입 힌트로 도구 설명과 입력 형식을 만들기 때문에, docstring이 모호하면 모델이 도구를 잘못 고릅니다. 관점을 바꿔 보면 도구 호출은 모델의 '행동'이고, 그 권한과 부작용은 실행하는 프로그램 쪽에서 책임집니다. 화면의 도구 호출 기록은 요청과 결과일 뿐, 모델의 생각 전체를 보여 주는 것은 아닙니다.

MCP는 앱 N개와 도구 M개를 하나씩 잇는 대신 규약 하나로 연결 수를 N+M으로 줄이는 발상이고, 자세한 예시는 부록의 MCP·Subagent·Hook 장면에 두었습니다. 앞 시간의 CLAUDE.md가 모델이 읽는 지침일 뿐 권한을 강제하지 않았던 것처럼, 오늘 쓰는 절차 파일도 작업 방법을 알려 줄 뿐 실행 권한은 실행 환경의 설정이 정합니다. 같은 자료를 매번 같은 규칙으로 정리하고 싶다면 넷 중 무엇이 맞을까요? 답은 Skill입니다. Skill은 어떻게 정리할지 절차를 적은 것이고, Hook은 'Claude Code가 파일을 고친 직후마다'처럼 언제 동작할지를 정하는 쪽이라 둘을 함께 쓸 수도 있습니다.

Attention은 Q·K 비교로 정한 비율대로 V를 모읍니다.

비율은 입력마다 새로 계산되는 값이며 학습된 매개변수와 다릅니다. 원 논문은 encoder–decoder 구조이고, 많은 생성 모델은 decoder 중심입니다.

  • Q·K·V 찾는 기준·이름표·내용비유 · 한 토큰 표현에서 나온 세 벡터
  • 그림 왼쪽: 헤드 하나의 계산softmax(QKT / √d) · V
  • 그림 오른쪽: 여러 헤드를 나란히헤드 = Q·K·V 계산 한 벌 · 헤드마다 다른 변환

앞의 RAG 구간에서 답이 틀리면 검색이 틀렸는지, 가져온 자료를 잘못 설명했는지부터 나눠 보자고 했는데, Agentic RAG는 그 판단의 일부를 그래프 안에 넣은 구조입니다. 화면 왼쪽 그림처럼 검색한 뒤 모델이 문서마다 질문과 관련 있는지 yes나 no로 판정하고, 관련 문서가 있으면 답변을 만들고 없으면 질문을 고쳐 다시 검색합니다. 오른쪽 코드는 그 판정을 정해진 형식으로 받도록 yes와 no 두 값만 허용하는 스키마를 모델에 연결하는 부분을 교육용으로 줄인 것입니다. 이 그림에서 모델이 하는 일은 관련성 판정이고, 어느 길로 갈지는 그 결과를 받은 조건부 Edge가 정한다는 점도 봐 두세요. 같은 계열인 Corrective RAG는 근거가 부족하면 웹 검색으로 보완하고, Self-RAG는 답변이 근거에 맞는지까지 평가하며, Adaptive RAG는 질문에 따라 검색을 안 할지, 한 번 할지, 여러 번 할지를 먼저 고르는데, 사내망에서는 웹 검색 자체를 쓸 수 없을 수도 있습니다. 판정 한 번마다 모델 호출이 늘어 시간과 비용이 커지므로 재검색 횟수에 상한을 두고, 상한에 닿으면 억지로 답하지 않고 근거를 찾지 못했다고 알리게 합니다. 평가 단계를 넣었다고 환각이 사라지는 것은 아니니 근거 확인은 계속 필요합니다. 오늘 실습한 기본 RAG로 충분한지부터 확인하세요.

Memory는 대화 중 상태를 저장하는 체크포인터와 대화를 넘어 남기는 저장소로 나뉘고, Context에는 모델 호출 앞뒤에서 로그를 남기거나 가드레일을 거는 미들웨어가 들어갑니다. Deep Agents는 LangGraph 위에 작업 계획 목록, 허용된 경로 안의 파일 도구, 긴 출력을 파일로 넘기는 오프로딩, 하위 작업 위임을 미리 묶어 둔 하네스이고, 오른쪽 코드는 그 설정의 인자 이름만 보여 주며 값은 생략했습니다. Claude Code도 하네스라고 했지만 LangGraph나 Deep Agents로 만든 것은 아니고, 모델을 둘러싼 실행 틀이라는 역할이 같다는 뜻입니다. 다음 장에서 볼 사내 배포 패키지 예시도 이런 구성으로 만든 참고 예시입니다. 다만 도구 몇 개를 짧게 호출하는 작업이라면 create_agent로 충분하고, 하네스 기능은 긴 작업, 파일 작업, 사람 승인 같은 요구가 생길 때 고르면 됩니다. 인자 이름은 설치 판본에 따라 달라질 수 있으니 공식 문서에서 확인하세요.

삭제, 셸 실행, 외부 시스템 변경처럼 되돌리기 어려운 행동은 모델이 요청하더라도 사람이 한 번 보고 결정하게 하는 것이 안전합니다. 화면 왼쪽 그림처럼 모델이 도구 호출을 요청하면 interrupt()로 그래프를 멈추고, 사람이 승인하면 도구를 실행하고, 거부하면 그 사유를 모델에게 돌려줍니다. 사람의 결정은 Command(resume)로 전달해 멈춘 곳부터 이어가는데, 멈춘 상태를 저장해 둘 체크포인터가 있어야 하고, 저장된 상태는 나중에 조회해 어느 시점에서 멈췄는지 확인할 수도 있습니다. 앞 장 코드의 interrupt_on처럼 Deep Agents에서는 어떤 도구 앞에서 멈출지 설정으로 선언만 해도 같은 효과를 냅니다. 오른쪽 화면은 사내 배포 패키지 예시로, 셸 명령을 실행하기 전에 도구 이름과 명령을 보여 주고 승인과 거부를 받는 장면입니다. 수강생 실습 화면은 아니고, 승인 카드 부분만 잘라 보여 드립니다. 오후 실습에서 Claude Code가 파일 수정이나 명령 실행 전에 승인을 요청했다면 그것도 같은 발상의 장치이고, CLAUDE.md나 프롬프트에 "하지 마"라고 적는 문장은 이런 멈춤 장치를 대신하지 못합니다.
