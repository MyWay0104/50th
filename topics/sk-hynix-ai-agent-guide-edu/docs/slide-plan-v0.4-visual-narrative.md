## 0. 빌더에게 주는 사용 지침 (먼저 읽을 것)

### 0-1. 이 문서가 하는 일과 하지 않는 일

- **한다:** 기존 52장의 구조·시간표·장면 ID를 유지한 채, (a) 장면마다 시각 자료를 지정하고, (b) 화면 설명 텍스트를 보강하고, (c) 기-승-전-결 서사를 명시하고, (d) 도입부에 참고 영상 장면 1장과 부록 4장을 추가한다.
- **하지 않는다:** 시간표·구간(B1–B7) 변경, 새 `data-skill` 값 발명, GSAP 트윈 추가, 사용자 최종 확인 전 PDF/PPTX export.
- 규칙이 충돌하면 우선순위는 `AGENTS.md` > `CLAUDE.md` > `DESIGN.md`(Notion 최소 적용) > 이 문서다. 이 문서는 **내용·구도·자료**를 정하고, 문법·규약은 저장소 스킬을 따른다.

### 0-3. 작업 순서

1. 이 문서 1~5절을 읽고 **6절 자산 준비 표**대로 `assets/img/` 하위에 이미지를 내려받거나 CSS 인포그래픽으로 만든다. 확보 못 한 것은 **7절 플레이스홀더 규격**으로 자리를 잡는다.
2. 8절(오전)·9절(오후)·10절(부록) 장면 콘티를 `data-scene-id` 기준으로 `index.html`에 반영한다. 신규 장면(G00, A07–A10)은 지정한 위치에 삽입하고 `--renumber`로 순번을 다시 매긴다.
3. 장면 하나를 고칠 때마다 "한 줄 요지 → 설명 문단 → 시각 자료 → 보조 라벨 → 출처 → speaker-note" 순으로 채운다(7-2절 텍스트 규칙).
4. 오전 22장 완료 시 validate + lint + `npm run snapshot -- topics/sk-hynix-ai-agent-guide-edu -- --at 4,9,29,54,79`로 대표 장면 확인 후 보고. 오후·부록 완료 시 동일.
5. 11절 QA 체크리스트로 자체 점검하고 `_workspace/ppt_qa_report.md`를 갱신한다. 그다음 사용자 overview 검토를 기다린다.
6. 판단이 필요한 항목(12절)은 임의 결정하지 말고 사용자에게 묻는다.

## 1. 이번 개정(v0.4)의 목표

현재 v0.3 덱은 구조·시간·사실 경계는 잘 잡혀 있으나 **글자만 있는 장면이 많고, 개념을 그림으로 보는 순간이 적다.** 사용자 피드백은 "텍스트 기반 설명이 부족한 느낌"이다. 이번 개정은 다음 다섯 가지를 목표로 한다.

1. **모든 장면에 시각 요소 하나 이상.** 논문·공식 문서의 그림(출처 표기), CSS/SVG 인포그래픽, 실제 화면 캡처 중 하나. 없으면 규격화된 플레이스홀더.
2. **설명 텍스트 보강.** 항목 1–4개만 있던 장면에 "한 줄 요지"와 "설명 문단(2–4문장)"을 추가한다. 발표 멘트를 통째로 옮기지 않고, 수강생이 PDF만 읽어도 무엇을 왜 배우는지 알 수 있는 수준으로 한다.
3. **기-승-전-결 서사 명시.** 하루를 네 막으로 나누고, 각 구간 첫 장면에 "이 구간의 질문"을 둔다. 앞 구간의 산출물이 다음 구간의 재료가 되는 연결을 화면에 드러낸다.
4. **참고 영상 1건 도입부 배치.** YouTube 영상(13절)은 재생하지 않고 썸네일 이미지 + 요점 텍스트로만 제시한다.
5. **후속 학습 부록 확장.** 4일 교안(Deep Agents·LangChain·LangGraph)과 5일 교안(LLM/RAG/Agent)의 심화 내용을 부록 A07–A10으로 추가해, 본문은 가볍게 유지하고 궁금한 사람은 부록으로 가게 한다.

장수: 본문 46 → **47** (G00 추가), 부록 6 → **10** (A07–A10 추가), **총 57장**. `#root data-duration="285"`.

## 4. 수강생 전제와 톤 (변경 없음, 요약)

- AI 경험자와 처음인 사람이 섞인 약 10명. VS Code를 설치 안 한 사람부터 웹개발 경험자까지.
- 강의 접근: ① 개념과 목적 → ② 동작 원리 → ③ 코드 흐름 → ④ 실습 예시 → ⑤ 헷갈리는 지점. 슬라이드 설명 문단도 이 순서로 쓴다.
- 톤: 단정적 과장 없이, "개념 예시"·"개인 기록"·"공개 Beta 설계 기반" 라벨을 유지. 사내 주소·모델명·키·설치 명령은 화면에 넣지 않는다.

## 7. 화면 구성 규칙

### 7-1. 플레이스홀더 규격 (이미지를 확보하지 못했을 때)

점선 박스(1px dashed `#a39e98`, 모서리 12px, 배경 흰색) 안에 다음 네 줄을 캡션체(28px, `#615d59`)로 적는다. 이 박스는 사용자가 `assets/`에 실제 파일을 넣으면 `<img>`로 교체한다.

```text
[IMG-PLACEHOLDER · P-S08]
넣을 자료: 실습 1 호출 결과 캡처 — 같은 질문, temperature 0.2 / 1.0 두 번
조건: 모델명·주소·키 가리기 · 실행일 표기 · 1600×900 이상
대체: 확보 전에는 이 박스를 그대로 두고 오른쪽 설명 텍스트만으로 진행
```

- 플레이스홀더 ID는 `P-<장면ID>` (한 장면에 둘이면 `P-S31`, `P-S31b`).
- 플레이스홀더가 화면의 절반을 넘지 않게 하고, 나머지 절반에 설명 텍스트를 둔다. 빈 박스만 있는 장면을 만들지 않는다.
- 논문 그림처럼 **빌더가 직접 확보할 수 있는 자료**는 플레이스홀더로 미루지 말고 6절 방법대로 확보한다. 확보 실패 시에만 플레이스홀더 + 실패 사유를 QA 보고서에 기록.

### 7-2. 텍스트 보강 규칙 (모든 장면 공통)

각 장면은 아래 여섯 층을 가진다. v0.3에서 ③이 없던 장면이 대부분이므로 이번에 채운다.

| 층 | 역할 | 크기 | 분량 |
|---|---|---|---|
| ① 구간 라벨 + 막 태그 | 위치 안내 | 28–32px | 구간 첫 장면만 |
| ② 제목 | 주제 하나 | 72–88px | 1줄 |
| ③ **한 줄 요지** | 이 장면에서 기억할 한 문장 | 40–44px, 파랑 밑줄 | 1문장, 40자 이내 |
| ④ **설명 문단** | 왜·어떻게 (①개념 ②원리 ③코드/실습 연결) | 32–36px | 2–4문장, 120자 이내 |
| ⑤ 시각 자료 + 캡션 | 그림·표·코드·캡처 | 캡션 28px | 1개 이상 |
| ⑥ 보조 라벨·출처 | "개념 예시"/"개인 기록", 출처 | 28px | 1–2줄 |

- 설명 문단은 **수강생이 읽는 문장**이다. 발표 멘트(강사 1인칭)를 그대로 넣지 않는다. "저는"→"강사는", "~해 보세요"→"~한다"로 바꾼다.
- 설명 문단에 넣을 내용 우선순위: (1) 왜 이 개념이 다음 실습에 필요한가 (2) 흔한 오해 한 가지와 정확한 표현 (3) 코드 어디를 보면 되는가.
- 오해 방지 문장은 조사정리 5절의 표현을 그대로 쓴다(11-2절 체크리스트).
- `.speaker-note`는 v0.3 내용을 유지하되, 이번에 추가한 그림을 가리키는 문장("화면 왼쪽 그림에서 …")과 교안 연계 설명 1–2문장을 덧붙인다.
- 실습 안내판(S08/S13/S19/S20/S26/S32/S37/S40–S43)은 ③·④ 대신 "이 실습에서 관찰할 것" 2문장을 두고, 시간 배분 숫자 블록을 유지한다.

### 7-3. 인포그래픽 공통 스타일

- 선 2px `#31302e`, 화살표는 선 끝 삼각형, 상자 모서리 12px, 상자 배경 흰색 + 헤어라인.
- 강조는 파랑 `#0075de` 테두리 또는 밑줄 하나만. 상태 표시가 꼭 필요할 때만 초록 `#1aae39`/주황 `#dd5b00` 점.
- "모델 영역"과 "프로그램 영역"처럼 **책임이 다른 영역은 배경 톤으로 구분**(오프화이트 vs 흰색)하고 영역 이름을 좌상단에 적는다. 이 구분이 오늘 강의의 중심 메시지와 직결된다.
- 그림 안 글자는 32px 이상. 그림 하나에 상자 7개 이하.
- 개념도에는 "개념 예시 · 측정값 아님" 캡션을 반드시 둔다.

#### S09 · 외부 자료가 필요한 질문 (`compare`)

#### S10 · RAG의 기본 구조 (`steps`)

- 유지: 3단계(준비·분할 / 검색 / 답변).
- 보강: 한 줄 요지 "미리 준비하는 인덱싱과 질문할 때의 검색·생성, 두 시점이 있다." 설명 문단 "인덱싱은 문서를 로드하고, 검색하기 좋은 크기로 나누고(청킹), 의미를 숫자 벡터로 바꿔(임베딩) 저장소에 넣는 과정이다. 질문이 오면 같은 방식으로 벡터를 만들어 가까운 조각을 찾고, 그 조각을 질문과 함께 모델에 전달해 답을 만든다. 벡터 저장소는 검색 구현의 한 방법이며 키워드 검색(BM25)도 있다. RAG는 모델을 학습시키지 않으므로 다음 질문에서 자료를 기억하지 않는다." 시각 자료: `b2/rag-pipeline.svg` 2단 파이프라인 — 상단 "미리 준비" 톤: 문서 → 로드 → 분할 → 임베딩 → 벡터 저장소; 하단 "질문할 때" 톤: 질문 → 임베딩 → 유사 조각 k개 → 프롬프트(근거+질문) → LLM → 답변+출처. 아래 미니 띠 `b2/chunk-overlap.svg` "chunk_size·overlap: 너무 작으면 문맥 손실, 너무 크면 노이즈" (교안-4일 텍스트 분할 요지).
- 코드 위치 라벨: "자료 준비(수집·분할) 부분 · 검색 부분 — 실습 가이드 해당 장".
- 출처: Lewis 2020 · LangChain Retrieval · 교안-4일 RAG 파이프라인·텍스트 분할 · 교안-5일 87–88쪽(재구성).

#### A08 · Agentic RAG — 검색 결과를 평가하고 다시 검색하기 (`steps`) — **신규**

- 한 줄 요지: "Naive RAG는 항상 1회 검색; Agentic RAG는 관련성을 평가해 재검색·재작성·웹 검색으로 분기한다."
- 설명 문단: "본문 S14에서 '검색 실패 vs 생성 실패'를 나눴다면, Agentic RAG는 그 판단을 그래프 안에 넣는다. retrieve → grade_documents(LLM이 문서별 관련성 yes/no 판정, structured output) → 관련 문서가 있으면 generate, 없으면 rewrite_query 후 다시 retrieve. Corrective RAG는 부족하면 웹 검색으로 보완하고, Self-RAG는 생성 후 환각·답변 품질까지 평가해 되돌린다. 재검색 루프는 최대 횟수를 제한한다. 각 판정마다 LLM 호출이 늘어 비용·시간이 커진다."

- 출처: 교안-4일 하네스(Harness)·4대 구성 요소·스토리지 백엔드·Middleware · 교안-5일 258·273–278쪽 DeepAgent(재구성) · 현업가이드 5장.

#### A10 · HITL — 사람의 승인을 흐름 안에 넣기 (`steps`) — **신규**
