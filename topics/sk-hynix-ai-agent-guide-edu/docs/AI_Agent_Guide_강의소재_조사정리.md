## 1. 가장 먼저 잡을 중심 메시지

**“LLM에게 맡길 일과 코드·데이터·사람이 책임질 일을 구분하면, 비전공자도 작은 업무 도구부터 만들고 개선할 수 있다.”**

현재 실습 구성에는 이 메시지를 보여줄 재료가 충분하다. 오전에는 LLM의 한계를 경험하면서 데이터와 도구를 연결하고, 오후에는 Claude Code를 사용해 그 프로그램을 개선한다. 이렇게 연결하면 오전의 LangChain과 오후의 Claude Code가 별개의 제품 강의로 끊기지 않는다.

수강생에게 남길 성과는 다음 네 가지로 정리하는 것을 제안한다.

1. 모델, API, RAG, Tool, Agent가 각각 무엇을 하는지 자신의 말로 설명한다.
2. 업무 요구를 보고 단순 스크립트·정해진 작업 흐름·Agent 중 필요한 수준을 고른다.
3. AI에게 목표뿐 아니라 입력·출력·제약·완료 조건을 전달한다.
4. 만들어진 결과를 근거 데이터, 다른 입력, 실패 상황으로 검증한다.

이는 **교육 설계 제안**이다. “하루 만에 개발 전반을 숙달한다”는 목표보다, 다음 업무에 다시 적용할 수 있는 행동을 목표로 삼는다. 복잡성은 필요할 때 추가한다는 기준은 Anthropic의 [Building effective agents](https://www.anthropic.com/engineering/building-effective-agents)와도 맞는다.

근거의 성격은 다음처럼 구분한다.

- **공식 확인:** 논문·공식 문서가 설명하는 개념과 기능.
- **개인 기록:** 사용자의 저장소, 블로그 보관본, 대화, 메모리에 남아 있는 경험과 설계.
- **교육 제안:** 그 근거를 이번 교육에 적용한 구성·실습 아이디어.
- **미확인:** 사내 운영 환경, 최종 실습 판본, 현재 배포 성능 등 이번 조사로 확인하지 못한 내용.

## 4. 개인 자료에서 건진, 강의의 차별점이 될 소재

### A. Part Finder: “말을 잘하는 모델”에서 “근거를 지키는 업무 도구”로

**확인한 기록:** 공개 Beta 저장소 README는 CSV/SQLite의 후보 데이터를 검색하고, 후보에 있는 Part Number만 답변에 사용하며, 파트 종류와 vendor/equipment 조건을 검증하는 설계를 설명한다. 외부 Vector DB 없이 로컬 TF-IDF 검색도 사용한다. 이는 공개 PoC의 설명이며 현재 사내 운영 버전과 동일하다고 확인한 것은 아니다. [공개 README](https://github.com/MyWay0104/Part_Number_Finder_Beta/blob/main/README.md)

**강의에서 건질 메시지:** 모델이 질문을 이해하는 능력과, 결과가 실제 데이터에 존재하고 조건에 맞는지를 확인하는 일은 분리할 수 있다.

**발표 소재 제안:** 가상 카탈로그에서 “제조사 A의 로봇블레이드”를 찾는데 해당 조건의 품목이 없는 상황을 보여준다. 같은 제조사라는 이유로 다른 종류의 파트를 내놓는 실패와, “해당 조건 없음”을 답하는 처리를 비교한다. 성능 수치는 측정 자료가 있을 때만 사용한다.

**좋은 연결 지점:** SQL Tool 설명 직후. RAG가 항상 Vector DB를 요구하지 않는다는 예시이기도 하다.

### B. 부동산 Agent 개발 기록: “AI가 말하기 전에 숫자부터 세도록”

**확인한 기록:** 개인 글에는 분석 로직을 분리하고 입력 레코드에 근거해 집계한 뒤 설명하도록 바꾼 과정이 있다. 다른 글에는 저장 전 컬럼·단위·날짜 등을 검증하는 데이터 계약의 필요성이 나온다. [숫자 계산 분리](https://app.notion.com/p/3be0b3a58d4d81bf8829d52babe27fdd), [CSV 저장 전 검증](https://app.notion.com/p/3be0b3a58d4d813e8fcdee1351b256f1)

**강의 전환:** 도메인을 장비별 건수·공정별 합계 등 교육용 가상 데이터로 바꾼다. “같은 자료인데 집계 기준·단위·중복 처리에 따라 답이 달라진다”는 문제를 보여준다.

**수강생이 가져갈 기준:** 정확한 계산이 필요한 부분은 SQL/Python으로 처리하고, 입력 정의와 계산 결과를 먼저 확인한다. 개인 기록의 테스트 건수를 이번 교육 코드의 검증 결과로 제시하지 않는다.

### C. Dokmo: 코드는 통과했지만 사용자에게는 불편할 수 있다

**확인한 기록:** 수동 점검 문서에는 한글 이름 입력, 안내 부족, 복잡한 이동 경로, 화면 한국어화 등의 개선 항목과 처리 기록이 있다. README와 권한 테스트 문서는 화면 표시와 DB 접근 제어를 별도로 다룬다. [수동 점검 기록](C:/Users/swl01/workspace/nextjs-supabase-app/docs/hand-off/handoff-2026-09-12-review-manual.md), [Dokmo README](https://github.com/MyWay0104/dokmo/blob/main/README.md)

**강의 메시지:** “앱이 켜졌다”, “기능 테스트가 통과했다”, “사용자가 편하게 쓴다”, “허용된 데이터만 접근한다”는 서로 다른 확인 항목이다.

**발표 소재 제안:** 한 기능의 코드 설명보다 실제 사용자 동선의 전후 화면이 좋다. 예를 들어 가입 후 다음 행동을 찾기 어려웠던 화면과 안내를 보완한 화면을 비교한다. 화면의 버튼을 숨기는 것만으로 데이터 권한이 보장되지 않는다는 점은 한 문장으로 덧붙인다.

**범위:** 현재 사이트를 직접 사용하거나 배포 상태를 재검증한 결과는 아니다.

### D. “아키텍처를 더 잘 짰어야 했다”를 수강생이 쓸 수 있는 교훈으로

**사용자 회고:** 개발 후반의 작은 수정도 의존성 때문에 어려워졌다.

**교육 제안:** 처음부터 완벽한 구조를 만드는 목표 대신, 바뀌기 쉬운 부분의 경계와 입출력을 먼저 정한다. 간단한 실습에서는 다음 정도면 충분하다.

| 경계 | 맡길 역할 | 변경했을 때 확인할 것 |
|---|---|---|
| 화면 | 사용자 입력·진행 상태·결과 표시 | 빈 입력, 오류 메시지, 근거 표시 |
| 데이터 접근 | 기사 읽기·DB 조회 | 자료 없음, 접근 실패, 시간 제한 |
| 모델 연결 | 모델 요청·응답·도구 호출 처리 | 모델/API 호환성, 응답 형식 |
| 업무 규칙 | 조건 필터·집계·후보 검증 | 같은 입력의 기대 결과 |

PRD는 무엇을 만들지, 계획 문서는 어떻게 구현할지, 프로젝트 지침은 반복해서 지킬 규칙을 기록하는 데 쓸 수 있다. 다만 파일을 많이 만드는 것이 목적은 아니다. 작은 실습은 README 한 장과 분리된 함수 몇 개로 시작할 수 있다. [Dokmo 프로젝트 문서 체계](https://github.com/MyWay0104/dokmo/blob/main/README.md), [Claude Code 모범사례](https://code.claude.com/docs/en/best-practices)

### E. Obsidian: 개인 지식은 “원문 + 내 판단 + 검토된 정리”로 쌓기

**확인한 기록:** Claude Study 저장소는 원문 Raw, 재사용할 Wiki, 주제별 인덱스를 나누고, 원문 수집 시 “왜 가져왔나 / 내 목적 / 활용 방안”을 사용자가 직접 작성한다. `/ingest`로 정리한 Wiki는 검토 전 상태로 만들고, `/wiki-search`는 원문 근거를 확인한다. [Claude Study README](https://github.com/MyWay0104/claude_study/blob/main/README.md)

**강의 메시지:** 자료를 많이 저장하는 것만으로 나의 판단 기준이 생기지는 않는다. 왜 중요했는지, 무엇을 결정했고 무엇을 검증했는지를 함께 남긴다.

**Twin Agent 표현 제안:** “내 과거의 결정과 근거를 찾아, 내 판단 기준을 적용하는 데 도움을 주는 개인 보조 Agent.” 나와 동일한 수준의 사고·결정을 보장한다고 설명하지 않는다.

**실습 제안:** 원문 한 개와 본인 의견을 구분해 적고, AI에게 출처가 있는 요약·불확실한 점·다음 질문을 만들게 한다. 수강생이 한 번 검토한 뒤 다른 질문에 재사용한다.

## 6. 초보자가 헷갈리기 쉬운 개념을 설명할 재료

### 6-0. LLM 원리는 세 가지 질문으로 좁히기

**무엇을 입력받고 내놓나?** 일반적인 자기회귀 텍스트 생성 모델은 문장을 토큰이라는 처리 단위로 바꾸고, 문맥으로부터 다음 토큰의 분포를 계산한다. 선택된 토큰을 붙이고 다시 계산하는 과정을 반복한다. 토큰은 단어 하나와 항상 같지 않으며 분할 방식은 모델의 토크나이저에 따라 다르다.

**Attention은 무엇을 하나?** 각 위치의 표현을 만들 때 다른 위치의 정보를 얼마나 반영할지 계산하는 장치로 설명한다. 예를 들어 같은 단어도 주변 문맥이 달라지면 다른 의미로 쓰인다는 사례를 먼저 보여주고 구조 그림으로 연결한다. Attention을 사람의 의식이나 이해 능력과 동일시하지 않는다. 학습된 모델 매개변수와 입력마다 계산되는 attention 가중치는 구분한다. [Transformer 논문](https://arxiv.org/abs/1706.03762)

**왜 이렇게 다양한 일에 쓸 수 있나?** 대규모 사전학습으로 얻은 능력에 지시 수행을 위한 후속 학습 등이 더해져, 요약·분류·코드 생성 같은 여러 작업을 언어로 요청할 수 있다. 다음 토큰 예측이라는 기본 원리를 설명하되, 그것만 말하고 데이터·규모·학습 방법의 영향을 생략하지 않는다. 일반적인 추론 요청에서 질문을 추가한다고 모델 매개변수가 곧바로 재학습되는 것은 아니다. [지시 수행 학습 연구](https://arxiv.org/abs/2203.02155), [LangChain 모델 개요](https://docs.langchain.com/oss/python/langchain/models)

발표 그림 후보는 `질문 → 토큰 → 문맥 계산 → 다음 토큰 선택 → 반복`이다. 이어서 temperature가 마지막 선택 과정에 영향을 준다는 설명으로 첫 실습에 연결한다. 같은 질문을 3~5회 비교하되 모든 호출에서 눈에 띄는 차이가 반드시 나타난다고 예고하지 않는다.

### 6-1. 모델을 ‘당겨 쓴다’는 말 풀기

| 요소 | 초보자 설명 | 실습에서의 예 |
|---|---|---|
| 모델 | 학습된 매개변수로 입력에 대한 다음 출력을 계산하는 핵심 | 사내 제공 모델 |
| 추론 서버 | 모델을 실행하고 여러 요청을 받는 서버 프로그램 | vLLM, 로컬 학습 예시의 Ollama |
| API | 다른 프로그램이 요청·응답을 주고받는 약속 | 메시지와 옵션을 보내고 결과를 받는 HTTP 요청 |
| SDK | API 호출을 편하게 작성하도록 돕는 라이브러리 | Python에서 제공되는 클라이언트 객체 |
| LangChain | 모델·메시지·도구 등을 공통 방식으로 연결하는 프레임워크 | ChatOpenAI, tool, agent 구성 |
| 애플리케이션 | 사용자가 실제로 조작하는 전체 프로그램 | Streamlit 앱, Claude Code |

클라이언트 코드에 `OpenAI` 또는 `ChatOpenAI`가 등장하더라도 실제 요청 목적지는 설정한 서버 주소에 달려 있다. 또한 “호환 API”가 모델 기능·모든 옵션·도구 호출까지 동일함을 뜻하지는 않는다. [사용자의 API·SDK·LangChain 비교 노트](C:/Users/swl01/workspace/00_sdk_vs_api/api_vs_sdk_vs_langchain.md), [vLLM 서버 문서](https://docs.vllm.ai/en/latest/serving/online_serving/)

### 6-2. Tool 호출은 눈으로 확인할 수 있는 흐름으로

1. 프로그램이 모델에게 도구 이름·설명·입력 형식을 알려준다.
2. 모델이 도구 호출 이름과 인자를 반환한다.
3. 프로그램이 실제 Python 함수나 SQL 조회를 실행한다.
4. 실행 결과를 모델에게 돌려준다.
5. 모델이 답하거나, 필요하면 다음 도구를 요청한다.

`@tool`은 보통 함수 정보에서 도구 설명과 입력 형식을 만드는 데 사용된다. 모델이 Python 함수를 자기 내부에서 실행하는 것은 아니다. 화면에는 도구 호출·결과·상태를 보여주고, 이를 모델의 숨겨진 사고 전체를 관찰하는 것처럼 설명하지 않는다. [LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools), [Function calling](https://developers.openai.com/api/docs/guides/function-calling), [개인 블로그 보관본](https://app.notion.com/p/3be0b3a58d4d81888a74d14cd8a0ee30)

### 6-3. RAG에서 ‘검색이 잘됐다’를 어떻게 확인할까

문서 수집 → 본문 확인 → 적절한 단위로 분할 → 검색 → 근거와 함께 답변 순서로, 각 단계의 결과를 확인한다. 임베딩은 내용을 수치 벡터로 바꾸는 과정, Vector DB는 그 벡터와 관련 자료를 저장·검색하는 역할로 구분한다. 사용한 도구가 임베딩 호출을 대신해도 임베딩 모델 자체와 동일한 것은 아니다. [개인 글: ChromaDB와 임베딩](https://app.notion.com/p/3be0b3a58d4d81f989a5c776ff1025de)

메타데이터는 부가 장식이 아니라 검색과 적용 범위를 정하는 정보다. 출처 URL, 발행일, 문서 버전, 장비·제조사, 적용 기간처럼 **답변에서 구분해야 하는 조건부터** 역으로 설계한다. “승인 필요” 같은 값을 기록하는 것만으로 승인이 강제되지는 않으며 실제 프로그램에서 처리해야 한다. [Metadata 적용](https://app.notion.com/p/3be0b3a58d4d81b683cfc8275557c126), [설계 방법](https://app.notion.com/p/3be0b3a58d4d818cbea3fb0839319590)

### 6-4. SQL Tool과 검증

이번 실습에서 접근하는 DataLake의 SQL 엔드포인트를 기준으로 설명한다. DataLake 전체를 항상 RDBMS와 같은 개념으로 설명하지 않는다.

- 테이블 구조, 날짜 기준, 단위, 결측값 의미를 제공한다.
- 읽기 전용 권한, 접근 가능한 테이블, 조회 시간·결과 크기 제한을 실제 실행 계층에 적용한다.
- 정답을 아는 작은 데이터로 SQL 집계와 출력 설명이 일치하는지 확인한다.
- 조회 결과가 없거나 도구 호출이 실패하면 이를 구분해 알린다.

프롬프트에 “위험한 SQL을 실행하지 마”라고 적는 것만으로 접근 제한을 대신하지 않는다. [LangChain SQL Agent 가이드](https://docs.langchain.com/oss/python/langchain/sql-agent)

수강생 요청문 템플릿:

> 목표: 무엇을 개선할지.  
> 입력: 파일·컬럼·예제와 필요한 맥락.  
> 출력: 사용자가 받는 결과 형식.  
> 범위: 이번에 변경할 기능.  
> 제약: 사용할 환경·자료·라이브러리 조건.  
> 완료 기준: 어떤 입력에서 어떤 결과가 나와야 하는지.

수강생이 결과를 받은 다음에는 “이 데이터가 들어오면 어떤 순서로 처리되는가”, “조건을 하나 바꾸면 어느 부분을 바꿔야 하는가”를 설명하게 한다. Python 학습 프로젝트에서 사용 중인 입력 변형·예상 결과 비교 방식을 이번 실습에 축소 적용할 수 있다. [교육 규칙](C:/Users/swl01/workspace/00_python-study/docs/TEACHING_PROTOCOL.md)
