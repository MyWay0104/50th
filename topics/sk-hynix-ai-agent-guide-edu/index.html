포함 관계를 나타낸 그림 · 연표가 아님

  • AI 안에 머신러닝, 그 안에 딥러닝
  • 현대 LLM은 주로 딥러닝 기반
  • 2017년 Transformer 등장문맥을 다루는 방식을 바꾼 구조

Attention과 문맥

개념 예시
같은 '배', 다른 문맥
디저트로 배를 먹었다
→
배 = 과일
항구에서 배를 탔다
→
배 = 선박

주변 단어가 표현에 반영되는 개념도 · 측정값 아님

  • 같은 표현도 문맥에 따라 다름
  • 다른 위치의 정보를 반영하는 계산
  • 데이터·규모·학습 방법으로 활용 확장

출처: Vaswani et al. 2017 · Ouyang et al. 2022

같은 '배'라도 '먹었다'와 함께 오면 과일, '탔다'와 함께 오면 선박으로 읽힙니다. Attention은 각 위치의 표현을 만들 때 다른 위치의 정보를 얼마나 반영할지 계산하는 장치이고, 이 값은 입력마다 새로 계산되므로 학습된 모델 매개변수와는 다릅니다. 참고로 원 논문은 번역용 encoder–decoder 구조였고, 오늘날 많은 생성 모델은 decoder 중심 구조를 씁니다. 데이터·규모·학습 방법이 발전하며 쓰임이 넓어졌지만, 이를 어느 순간의 특이점으로 단정하지는 않겠습니다. 임베딩·Vector DB는 검색 방법 중 하나 · 모델을 다시 학습시키지 않음

출처: Lewis et al. 2020 · LangChain Retrieval 가이드

RAG는 검색한 자료를 이번 답변을 만들 때 사용하는 방식입니다. 자료를 나누는 이유는 긴 문서 전체가 아니라 질문에 필요한 부분을 찾기 위해서입니다. 임베딩은 내용을 숫자 표현으로 바꾸는 과정이고, Vector DB는 그 표현과 원문을 보관하고 검색하는 저장소인데, 키워드 검색처럼 다른 방법도 있어 항상 필수는 아닙니다. 그리고 RAG는 모델 가중치를 바꾸는 학습이 아니므로, 다음 질문에서 그 자료를 모델이 기억하는 것도 아닙니다. 기사 한 편 전체를 요약하는 것과 질문에 맞는 근거를 찾아 답하는 것의 차이를 한 문장으로 말해 볼까요?

출처: Lewis et al. 2020 (Retrieval-Augmented Generation) · LangChain Retrieval 가이드 · Part Number Finder Beta 공개 README

B2 실습의 RAG 구조를 한 단계 더 나누면, 미리 해 두는 청킹·임베딩과 질문할 때 하는 검색으로 볼 수 있고, 어느 단계도 모델을 다시 학습시키지 않습니다. 청킹은 긴 문서를 찾기 좋은 단위로 나누는 일이고, 임베딩은 조각을 뜻이 가까운 것끼리 찾을 수 있는 벡터로 바꾸는 일이며, 키워드 검색은 같은 단어가 들어 있는 조각을 찾습니다. 어느 방식이 나은지는 내 자료와 질문으로 직접 비교해 봐야 하고, Part Finder 공개 Beta처럼 Vector DB 없이 단어 빈도로 검색하는 구성도 있습니다. 메타데이터는 장식이 아니라, 출처·발행일·장비처럼 답변에서 구분해야 하는 조건부터 거꾸로 설계합니다. 다만 "승인 필요" 같은 값을 적어 두는 것만으로 승인이 강제되지는 않고, 그 처리는 프로그램이 해야 합니다. 답이 틀렸을 때는 검색이 틀린 것인지, 찾은 근거로 잘못 답한 것인지부터 나눠 보세요.

LangChain, LangGraph, Deep Agents는 차례로 모두 배워야 하는 과정이 아니라, 필요한 제어 수준에 따라 고르는 선택지입니다. 오전 실습처럼 모델과 검색기, 도구를 연결하는 정도라면 LangChain으로 충분하고, 단순 호출 하나라면 SDK만으로도 됩니다. 단계와 분기를 직접 정하고, 상태를 저장했다가 중단한 곳에서 이어가거나 사람 확인 단계를 넣어야 한다면 LangGraph를 봅니다. Deep Agents는 LangGraph 위에 계획, 파일 공간, 하위 작업 위임을 미리 묶어 둔 하네스로, 여러 단계로 이어지는 긴 작업에 맞춰져 있습니다. 예제 코드 길이가 다르다고 성능이 다른 것은 아니며, 같은 과제로 비교한 결과가 아니면 성능 비교로 읽지 않습니다. 내 업무에 흐름 제어가 정말 필요한지부터 확인해 보세요.

출처: Claude Code 문서 — Features overview · MCP · Subagents · Hooks

S36에서 Skill 옆에 짧게 보여 드린 세 기능을 조금 더 풀어 보겠습니다. MCP는 외부 시스템의 도구와 자료를 Claude Code에 전달하는 연결 규약이고, 기존 파일·명령 도구로 충분하면 추가하지 않아도 됩니다. Subagent는 예외 입력 점검이나 설정 위치 조사처럼 독립적인 하위 작업을 별도 맥락에서 맡기고 결과만 돌려받는 방식인데, 여러 개를 쓰면 비용과 조정 작업도 늘어납니다. Hook은 파일 수정 후 포맷처럼 정해진 시점에 설정된 동작을 실행하며, 명령을 실행하는 유형과 모델 판단을 쓰는 유형이 따로 있습니다. 세 기능은 상하위 단계가 아니라 서로 다른 역할이고 필요하면 함께 조합합니다. 실제 설치와 권한 설정은 사내 가이드의 승인된 방법을 따르고, CLAUDE.md에 적은 지침은 권한을 강제하지 않는다는 점도 기억해 두세요.
